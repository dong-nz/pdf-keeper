# Cover thumbnails — technical reference

**Since v0.0.1, updated in v0.0.4, v0.0.5, v0.0.7 and v0.0.8** · Requirements: FR-16 (MODIFIED in v0.0.4 — render width joins the cache identity, DR-113; further MODIFIED in v0.0.7 — finished covers reach the open view, DR-231), UI-04, defects D6 and D7, D17 (v0.0.5 — queue design only; FR-16 text unchanged); v0.0.8: FR-20 (protected-document cover gating, §3.3), FR-21 (rename re-keying, §3.4 — AC-106, AC-110) · User guide: [features/covers.md](../features/covers.md) · Spec: [SPEC-v0.0.1-covers.md](../../specs/SPEC-v0.0.1-covers.md) (v0.0.4 changes: [SPEC-v0.0.4.md](../../specs/SPEC-v0.0.4.md) §3.4 (D6), §3.5 (D7); v0.0.5 changes: [SPEC-v0.0.5.md](../../specs/SPEC-v0.0.5.md) §3.5 (D17), DR-133→DR-134; v0.0.7 changes: [SPEC-v0.0.7.md](../../specs/SPEC-v0.0.7.md) §3.19 (FR-16 further MODIFIED), §3.12 (row cover geometry), DR-231, DR-237, DR-188/DR-189; v0.0.8 changes: [SPEC-v0.0.8.md](../../specs/SPEC-v0.0.8.md) §3.3, §3.4)

## Generation (`src-tauri/src/covers/`)

- `pdfium-render` renders page 1 at target width `RENDER_TARGET_WIDTH = 640` px — raised from 220 in v0.0.4 (D7) so the largest display size (320 px card at 2× device-pixel ratio) is a downscale, never an upscale. PNG output into `<app_data>/covers/`.
- Cache key: `cache_key(path, size, mtime, width)` — content-addressed by source file identity **plus the renderer's current target width** (FR-16 as modified by DR-113). A changed file or a changed render target produces a new key and the old PNG is swept by `sweep_orphans` (startup maintenance) — raising the render width re-keys every entry, so existing libraries re-render in the background with no explicit cache wipe.
- `pdfium_binary_present()` gates rendering: without the bundled pdfium binary the app runs fully, simply without covers (graceful degradation, no errors).
- Packaging (DR-59): `bundle.resources: ["binaries/*pdfium*"]` ships the platform library `fetch-pdfium.mjs` downloaded (`pdfium.dll` / `libpdfium.so` / `libpdfium.dylib`) into `binaries/` beside the installed exe. `bind_candidates()` binds in order: exe directory → `binaries/` beside the exe (packaged) → `cwd/binaries` (dev). Windows layout verified from an administrative MSI extraction; the installed exe runs against it.

## Queue model (D17 as shipped, DR-134)

- `CoverQueue` (`mpsc` handle, `Clone`): `import_paths` / `import_folder` enqueue a `CoverJob` after each row commit and return immediately — cover work never blocks import (DR-17).
- `start_pool(dir, sink)` starts the pipeline (D17): **one render worker** binds pdfium and produces decoded images, feeding **N PNG-encode workers** that encode and write. The split is the measured one (DR-134): pdfium load+render is 4 % of a cover's time and the bundled pdfium binary is not safe for concurrent calls (pdfium-render #262), so pdfium is touched by exactly one thread — as released in v0.0.1–v0.0.4; the PNG encode is 96 % and is pure Rust and thread-safe. Encode-pool size: default `min(4, max(1, ⌊cores/2⌋))`; the `PDFKEEPER_COVER_WORKERS` override is clamped to 1..8 (`pool_size` takes the override as an argument so the clamp is testable without process env). A bounded handoff (capacity 2 per encoder) keeps a stalled encoder from letting the renderer run ahead unbounded. `PDFKEEPER_COVER_WORKERS=1` collapses the pipeline to the released serial behavior.
- `ProgressTracker` keeps the released event contract across workers (R5.1): the queue counters and the throttle (every 25 completions + final drain, AC-33 unchanged) live in the shared tracker; a gate makes the event stream monotonic — every published count is read and stamped under one lock — and the final drain event is guaranteed. Progress goes through `EventSink::progress` → `library_job_progress` events as before. The v0.0.1–v0.0.4 single `start_worker` is gone.
- A missing pdfium binary leaves drain-only behavior: rows are counted, no images are produced, nothing errors (graceful degradation, `pdfium_binary_present()` gate unchanged).
- Startup backfill: `enqueue_missing_covers(conn, queue)` queues every document without a cache hit (e.g. after a cache directory wipe). `rescan` enqueues jobs for files whose size/mtime changed. A failed render skips that document (row shows the placeholder); it never fails the import or the batch.

## UI (`ui/src/`)

- `DocumentRow` / grid card render the cached path returned in `DocumentDto.cover_path` (mapped to a file URL in `query.rs::map_row`); placeholder tile when absent.
- **Display sizes (current):** the list cover is `ROW_COVER_HEIGHT = ROW_HEIGHT − 2 × ROW_COVER_GAP` = **51×72 at the 88 px row with an 8 px gap** (all three derived from shared constants/tokens in `lib/virtual.ts` + `--row-height`/`--row-cover-gap`, so they cannot disagree — v0.0.7 §3.12, DR-188/DR-189; the history: 34×48 at 48 px rows in v0.0.1–v0.0.2, 45×64 at the 64 px row from v0.0.3); a card's cover is `coverWidth(cardWidth) = cardWidth − 2 − 2 × CARD_CONTENT_PAD` at the shipped 218:309 inner ratio — the 5 px content inset of v0.0.7 (DR-245; see sorting-and-views.md). **Changed in v0.0.4 (D6):** `.cover-wrap` no longer carries 10 px of padding — the cover fills the inner box, so the image can no longer cross the card border at wide card widths, and `cardHeight(cardWidth) = coverHeight(cardWidth) + CARD_TEXT_BLOCK` (the padding term left the formula; `virtual.test.ts`'s card-height and row-block cases were re-derived). **Changed in v0.0.4 (D7):** the rendered asset is 640 px wide (was 220), so the upscale above 220 px — the recorded limitation of v0.0.3 — is gone: every display size up to a 320 px card at 2× device-pixel ratio downscales from a render larger than it needs. `DocumentDto` still carries no size; the layout derives everything from the constants.
- Cover progress merges into the import progress UI (`library_job_progress`).
- **Cover appearance on generation completion (v0.0.7, §3.19, DR-231/DR-237).** Two halves: (1) the backend stops promising a cover file that isn't there — `query.rs::map_row` delivers `cover_path` only when the cache file exists (the released `enqueue_missing_covers` rule moved into the read path: an unprepared row carries no path, renders the glyph, and issues no asset request); (2) the store re-queries when cover work completes — `#coverRefresh` (`state/library.svelte.ts`): a trailing `debounce` (250 ms) collapses the burst of cover progress events (the queue emits every 25 + the final drain) into ONE `#refreshCoverRows()` — a re-run of the current search over the current view — so finished covers appear in the open list or grid without a reload or view switch (AC-100). The re-query is the store's own search path — no second data source, no polling.

## Change history

- 2026-11-03 (v0.0.1) — First shipped. Migrated from SPEC-v0.0.1-covers.md, corrected to the verified code: 220 px target width, throttled progress events, startup backfill + orphan sweep as built. Packaging corrected before freeze (DR-59): resources glob bundles the Pdfium library on every platform, not only Windows.
- 2026-11-04 (v0.0.3 — display metrics only, DR-99) — List covers grew with the taller row (34×48 → 45×64, derived from `ROW_HEIGHT`) and card covers became a function of the derived card width instead of a fixed 220 px box. **No change to generation, cache keys, the queue, the 220 px render target or the placeholder path** — the 49 Rust tests here are the same tests as in v0.0.1. The upscale above 220 px is recorded as a known limitation of this release, not as a fixed defect.
- 2026-11-05 (v0.0.4 — D7 + FR-16 MODIFIED per DR-113, D6) — Render target 220 → 640 px; `cache_key` gains the render width as its fourth part, so the raised target re-keys every existing entry and `sweep_orphans` retires the old PNGs through the machinery that already existed — no cache wipe, no second staleness rule. The v0.0.3 upscale limitation is closed by this. Card geometry (D6): `.cover-wrap` loses its 10 px padding, the cover fills the card's inner box exactly, and `cardHeight` loses the padding term (`coverHeight + CARD_TEXT_BLOCK`); `virtual.test.ts` card-height/row-block cases re-derived; the real-app inset check passes at 140–320 px card widths in 900/1280/1900 px windows (AC-35). Queue, events, backfill, the placeholder path and the missing-binary gate unchanged.
- 2026-11-06 (v0.0.5 — D17 per DR-133→DR-134, AC-57) — **The queue became the render/encode pipeline:** one render worker (pdfium on exactly one thread — the bundled pdfium binary is not concurrency-safe, pdfium-render #262) feeding `min(4, max(1, ⌊cores/2⌋))` PNG-encode workers (`PDFKEEPER_COVER_WORKERS` override clamped 1..8), bounded handoff (capacity 2 per encoder), `ProgressTracker` gate preserving the released event contract (25-job throttle + guaranteed final drain — AC-33 unchanged). The DR-133 per-worker-pdfium design is recorded and superseded: it aborted the suite intermittently (3/15 runs) and the cost split (render 4 %, encode 96 %) made parallel rendering pointless. `start_pool` replaces `start_worker`; `start_worker` removed. **Measured: the real-app 10 000-document backfill runs at 79.1 covers/s — 2.9× the 27/s serial baseline (AC-57).** Cache keys, the 640 px render target, backfill, orphan sweep, the placeholder path and the missing-binary gate are unchanged; no new dependency and no Cargo.toml change (the DR-133 feature toggle was reverted with default features restored).
- 2026-11-09 (v0.0.7 — FR-16 further MODIFIED §3.19, DR-231/DR-237; row cover geometry §3.12 DR-188/DR-189; card content inset DR-245) — **Covers reach the open view.** The read path delivers `cover_path` only when the cache file exists (DR-237 — the row renders the glyph and issues no request for a missing file); the library store's cover-completion re-query (`#coverRefresh` trailing debounce → one `#refreshCoverRows()`) makes finished covers appear in the open list or grid without a reload or view switch (AC-100). Row cover 45×64 → 51×72 with the 88 px row and 8 px gap (shared tokens/constants, skeletons and windowing follow); card covers carry the 5 px content inset (DR-245). **Generation, cache keys, the 640 px render target, the queue and its event contract are unchanged — the v0.0.7 encoder tuning (D19) applies to the reader page path only; covers keep the balanced default encoder.** New tests: `cover_path_is_delivered_only_when_the_cache_file_exists`; `flowCovers` live-appearance checks; `flowRowDesign` re-derived to the new row geometry (AC-88). Verified: Phase A feature-lane runs 2026-11-09 green per the Build ledger, plus the user's Phase-B real-app confirmation (Phase C skipped for this release, DR-248) — cover lanes green, live appearance observed in the running app.
- 2026-11-10 (v0.0.8 — FR-20 §3.3 cover gating; FR-21 §3.4 re-keying) — **Two queue behaviors, pipeline unchanged.** (1) A protected document with no stored password is enqueued and rendered as the glyph fallback (`covers::tests::a_protected_document_gets_no_cover_until_its_password_is_stored`); the queue passes the row's stored `pdf_password` to the render when present, and after a remembered unlock the document is re-enqueued — the real cover replaces the glyph through the released DR-231 appearance path (`library::stored_password_round_trips_and_requeues_the_cover`). (2) A rename re-keys the cover (the cache key composes from the path, M3): the document is enqueued under the new key and the stale entry is removed by the existing orphan sweep (`covers::a_renamed_document_renders_under_the_new_key_and_the_stale_entry_is_swept`). The multi-front pipeline, the 640 px render target, the key format and the sweep itself are unchanged. Verified by the Rust tests above (AC-106, AC-110) and the `flowProtected` / `flowRename` lanes' cover steps.
