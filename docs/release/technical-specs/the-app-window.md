# App window — technical reference

**Since v0.0.2 · updated in v0.0.3, v0.0.4 and v0.0.7** · Requirements: UI-07 (ADDED in v0.0.2), UI-11 (ADDED in v0.0.2, ramp selection MODIFIED in v0.0.3, D9 arrow-button suppression v0.0.4), UI-12 (ADDED in v0.0.2, MODIFIED in v0.0.3 — the app menu removed), UI-13 (ADDED in v0.0.3), defect D2 (fixed in v0.0.3), defects D3 and D9 (fixed in v0.0.4); v0.0.7: UI-37 (tooltip surfaces and full coverage, §3.11 — DR-212/DR-213/DR-216) · User guide: [features/the-app-window.md](../features/the-app-window.md) · Spec: [SPEC-v0.0.2.md](../../specs/SPEC-v0.0.2.md) §3.1, §3.8, §3.9 — decisions DR-73, DR-79, DR-87, DR-88 (corrected by DR-90), DR-89; [SPEC-v0.0.3.md](../../specs/SPEC-v0.0.3.md) §3.1, §3.2, §3.6, §3.8 — decisions DR-94, DR-99, DR-101, DR-103, DR-105, DR-106; [SPEC-v0.0.4.md](../../specs/SPEC-v0.0.4.md) §3.1, §3.7 — decisions DR-115, DR-122; [SPEC-v0.0.7.md](../../specs/SPEC-v0.0.7.md) §3.11 — decisions DR-212, DR-213, DR-216 (the vertical content inset of the same release is specified in [sorting-and-views.md](sorting-and-views.md) §3.10)

The OS title bar is removed and the app draws its own window controls, its own scrollbar styling, and — since v0.0.3 — an icon-only control row with tooltips and a working drag region. No product logic is involved: this feature is window configuration, frontend components, one thin command, and one stylesheet rule set.

## Window configuration (`src-tauri/tauri.conf.json`)

- `app.windows[0]`: `title: "PDF Keeper"`, `width: 1280`, `height: 800`, `minWidth: 900`, `minHeight: 600`, **`decorations: false`** — the frameless window the toolbar's controls replace.
- `app.security.csp` unchanged from v0.0.1 (DR-44): `default-src 'self'; img-src 'self' asset: http://asset.localhost; style-src 'self' 'unsafe-inline'`. Because `connect-src` falls back to `'self'`, Tauri's `ipc://localhost` custom-protocol fetch is blocked and every command travels over the documented fallback transport — a JSON message through `window.chrome.webview.postMessage` (measured at the command boundary, DR-89). The app behaves identically; the smoke harness observes the same boundary the app uses.
- Version identity: `productName: "PDF Keeper"`, `version: "0.0.4"` — the single source the About dialog and the Settings dialog's Library section read. `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock` and `ui/package.json` carry the same 0.0.4 so no build artifact reports a different release than the packaged app.

## Capabilities (`src-tauri/capabilities/default.json`)

`core:default`, `core:window:allow-minimize`, `core:window:allow-toggle-maximize`, `core:window:allow-close`, **`core:window:allow-destroy`**, **`core:window:allow-start-dragging`**, **`core:window:allow-set-size`**, `dialog:allow-open`, `dialog:allow-confirm`, `opener:allow-open-path`. The v0.0.3 additions are each the permission an action the app already performs needs in order to complete: `allow-start-dragging` is what Tauri's own `drag.js` calls when a mousedown lands in the declared drag region (DR-103), and `allow-destroy` is what `@tauri-apps/api/window`'s `onCloseRequested` wrapper calls to finish a close the handler did not prevent (DR-105 — without it the toolbar's Close button left the window open and the rejection surfaced as an unhandled promise rejection). No other capability is granted (R1.5); `core:default` still supplies the read-only window commands (`allow-is-maximized`, `allow-is-minimized`, …) that the controls and the harness read, and none of them was added by hand. The one v0.0.4 addition — `core:window:allow-set-size` — is different in kind: it is requested by the **smoke harness** (`plugin:window|set_size`, the AC-35/AC-39 width-matrix flows that resize the real window to 900/1900 px), not by product code; no product path calls it, and the capability file's description names its only caller (DR-122, chosen over a new product command that would bloat the whitelist for a test-only need, and over skipping the measurements the ACs name).

## Window controls (UI-07)

- `components/WindowControls.svelte` — three buttons at the toolbar's right end, 44px wide, full toolbar height, `aria-label` from the catalog and, since v0.0.3, the shared `Tooltip` wrapper instead of a native `title` (UI-13); the close button takes the danger hover treatment. `getCurrentWindow()` from `@tauri-apps/api/window`; the buttons call `minimize()`, `toggleMaximize()`, `close()` and nothing else.
- The Maximize button mirrors the window: `win.isMaximized()` is read once on mount and again on every `onResized`, and the result drives `data-maximized`, the glyph (`maximize` / `restore`) and the label. A failed read leaves the last known glyph — the control never changes state on an error, and no error is shown for a preference the user did not ask about.
- Dragging (D2, fixed in v0.0.3): `Toolbar.svelte`'s root carries **`data-tauri-drag-region="deep"`** and every control wrapper — `BrowseMenu`, the Select-mode toggle, `ViewMenu`, `SettingsMenu`, `SearchBox` (including the import control inside it), `WindowControls` — carries **`data-tauri-drag-region="false"`**. That is what Tauri's own rule requires: `isDragRegion` in `tauri-2.12.5/src/window/scripts/drag.js` walks `e.composedPath()` on mousedown, grants a bare or `"true"` attribute only when the target **is** the element carrying it, grants `"deep"` to any descendant, and stops the walk immediately at any clickable element that carries no attribute — so the v0.0.2 spelling made the strip respond only on its own padding and the gaps, which is why the window was hard to move and double-click-to-maximize was unreachable. Effect, measured: pressing the empty strip (including the padding around a control) starts `start_dragging`, pressing a control does not; a double click on the strip runs `internal_toggle_maximize` and a second one restores; a double click on a control is a click on the control and never maximizes. No configuration change: `decorations: false` stays.
- Closing: the app registers `onCloseRequested` to flush pending settings writes before the window goes (settings-and-appearance.md). Registering that listener moves the completion of an unprevented close onto the JS side — the wrapper calls `getCurrentWindow().destroy()` — which is why `core:window:allow-destroy` is granted (DR-105) and why the toolbar's Close button is the path the harness uses to end a session.
- Keyboard: the buttons are plain focusable buttons in the toolbar's tab order (`flowKeyboardAudit` asserts every toolbar control is tabbable). No new shortcut was added; the OS-level paths are untouched.

## App menu and About (UI-12 — app menu removed in v0.0.3)

- `components/AppMenu.svelte` — **removed in v0.0.3** (UI-12 as modified; the component is deleted, R7.4, and its catalog key `menu.app` with it — `i18n/coverage.test.ts` fails on an unused key, so the removal is enforced by the existing test rather than by a note). The control was a `bits-ui` DropdownMenu trigger immediately left of the window controls with exactly one item.
- The About surface is unchanged in every respect and is now reached from the Settings menu ([settings-and-appearance.md](settings-and-appearance.md)) as *About PDF Keeper…*.
- `components/AboutDialog.svelte` — the shared `Modal` (420px, focus-trapped, Esc and close button), showing two definition rows: the application name and the version. Since v0.0.3 the dialog's Escape is answered by `Modal.svelte`'s own guard rather than by the kit's escape-layer stack (DR-106, settings-and-appearance.md).
- `app_about(app: AppHandle) -> AboutDto { name, version }` (`src-tauri/src/commands.rs`) — a thin wrapper over `app.package_info()`, no service module needed because there is no product logic to test. The frontend contains no version string: the value the dialog displays is the value the packaged application reports, which is what `flowAbout` compares.

## Icon-only controls and tooltips (UI-13, v0.0.3)

- `components/Tooltip.svelte` — the single wrapper over the kit's Tooltip primitive (verified present in `bits-ui@2.20.3`: `bits/tooltip/exports.d.ts` exports `Root`, `Trigger`, `Content`, `ContentStatic`, `Arrow`, `Provider`, `Portal`). Contrast with `ToastStack`, which is hand-rolled because the kit shipped no Toast (DR-52): here the primitive exists, so behavior comes from the kit and every visual from tokens — 12px text, `--surface-0` on `--surface-1`-adjacent chrome, 1px `--border-hairline`, radius 6, no shadow. One `Tooltip.Provider` is mounted once in `App.svelte` with a short open delay; the kit's tether positions the content. Hover and keyboard focus produce the same tooltip (R4.4). The nesting question raised before coding — a `Tooltip.Trigger` wrapped around another kit primitive's trigger — composed on one element in the installed version, so the planned fallback wrapper element was not needed.
- Every control in the toolbar row is an icon button with no visible text: Browse, Select, View, Settings, the import control inside the search field, and the three window buttons. Each carries `aria-label` from the catalog and a tooltip with the same string; 8 controls, none text-bearing, none unnamed (measured). `.toolbar-actions` and its separators were deleted; the row uses one gap value and `--control-height` for every control, `--toolbar-height` unchanged at 52 (§5.3.7 metrics unchanged).
- A menu control shows its state **inside** its menu (checked items), never on the icon. The Select-mode toggle is the one control whose state shows on the control itself: `aria-pressed` plus the `--accent-quiet` fill.
- **v0.0.4 (D3, §3.1):** the control boxes are square and the glyph is centred inside them — the `.control` + `.icon-button` pairing had stacked two padding models and left every toolbar glyph ~2.6 px off the box centre. One centring rule now governs; measured in the running app at ±1 px for Browse, Select, View, Settings and the window buttons (AC-32, `flowActionParity`). Text-bearing controls (the search field, menu labels) keep their 10 px padding — the fix is about icon boxes only.
- **Tooltip surface — v0.0.7 (UI-37, §3.11).** `Tooltip.svelte`: `background: var(--surface-1)` (was `--surface-0`) plus `box-shadow: var(--shadow-overlay)`, keeping the 1 px `--border-hairline`, the control radius and `--text-primary` text — exactly the overlay recipe the menus (`.menu`) and modals (`.modal`) already carry, the ground the ramps assign to floating chrome. `--surface-0` was the same ground as the toolbar/rows behind the tooltip, so the box was invisible (the user-reported defect); the shadow separates a `--surface-1` tooltip from the `--surface-1` chrome it can land on. The text pair already exists on this ground (menus/modals render it) and the shipped pair-table guard covers it in both ramps. No new token (R4.5).
- **Never a scroll source — v0.0.7 (DR-212, mechanism completed DR-213/DR-216).** The settings dialog's Data location row is the last control of a scrolling section; its tooltip, rendered in the section's DOM flow, extended the modal's scrollable extent and summoned a scrollbar (a Phase-B defect). `Tooltip.Content` now carries the kit's `strategy="fixed"`: the content positions against the viewport and never contributes to any ancestor's scroll overflow; the positioner re-derives on scroll/resize, edge-flip unchanged. Fixed positioning holds only when no ancestor intercepts it as a containing block — two shipped mechanisms did exactly that (`.modal`'s `transform` and an ancestor `filter`), corrected by removing them in favor of an equivalent that does not create a containing block (DR-213/DR-216; the visual result unchanged).
- **Full coverage — v0.0.7 (UI-37).** The fourteen remaining native `title` attributes (row title/author/notes lines, card title/author lines, the missing flag and badge path, a category action, the delete dialog's note button, a column stepper, the reader chrome name and others across eight files) moved to the released wrapper pattern (the D4 pattern: kit trigger props merged onto the control element; text spans stay spans). OS-drawn native tooltips followed the *system* theme, not the app's ramp (UI-17/DR-101 independence), and clipped text had no label mechanism at all outside the kit; every ellipsized line now carries its full text in the app's own tooltip. Trigger behavior stated honestly: control tooltips open on hover and keyboard focus (unchanged); text-surface tooltips open on pointer hover — exactly what the native title did; the row/card `aria-label` still carries the full title for screen readers.

## Scrollbars (UI-11)

- `lib/design-tokens.css`: `--scrollbar-thumb` / `--scrollbar-track` in both ramps (light `#c9cfd8`, dark `#3b424e`, track transparent — the ramps' `--border-strong` values). Since v0.0.3 the ramp is selected by `:root[data-theme="dark"]` and each block declares its own `color-scheme` (`light` in `:root`, `dark` in the dark block), so UA-drawn chrome follows the ramp the app is actually showing — including an explicit Light/Dark choice against an OS set the other way (DR-101, [settings-and-appearance.md](settings-and-appearance.md)).
- `lib/base.css`, one rule set and nothing else: `html { scrollbar-color: var(--scrollbar-thumb) var(--scrollbar-track) }` and `* { scrollbar-width: thin }` (`color-scheme` moved to the ramp blocks, above). **`scrollbar-color` is inherited; `scrollbar-width` is not** — measured in the running app, which is why the width is declared for every element (DR-87; the draft's single-`html` spelling left every container but the root drawing the 15px platform bar). Older-WebKit fallback in the same block: `::-webkit-scrollbar` / `-track` / `-thumb` with the same tokens; engines that support the standard properties ignore the pseudo-elements.
- Consequence, measured: every surface that scrolls reserves a 10px gutter instead of 15px, so `containerWidth` grows 5px; `virtual.ts` measures `clientWidth` (already scrollbar-excluded) and AC-10's Auto computation re-measured unchanged (5 columns at a 1280px window). No `scrollbar-gutter` reservation (DR-73).
- **v0.0.4 (D9, §3.7, DR-115):** the WebKit fallback block now carries the one declaration it never had: `::-webkit-scrollbar-button` is suppressed. That unstyled pseudo-element was the only construct in the app able to draw arrow buttons at the ends of a scrollbar (the user-reported arrows on some systems; the mechanism was left unresolved when the item was accepted — OQ-30 — and this is the chosen fix). The standard properties remain what governs in this runtime (`scrollbar-width: thin` + `scrollbar-color` measured active, 10px gutter unchanged); the change alters nothing on engines that never drew buttons, and AC-38 verifies no arrow buttons at any scroll position in the real app plus a source check that the five scrollbar selectors remain the only scrollbar rules.
- Excluded deliberately: thumb hover/recolor-on-scroll — it would need per-surface `:hover` rules, which is the per-component styling UI-11 forbids (R1.6).

## Invariants

- The app's own window actions are minimize / toggle-maximize / close, plus the two completions those actions require (`start_dragging` for the strip, `destroy` for an unprevented close). No capability is granted for product behavior beyond those (R1.5, DR-88/DR-90, DR-103, DR-105). The single verification-only grant is `allow-set-size` for the harness width matrix, recorded with its reason at the fork (DR-122) — the exception is named, not silent.
- The version shown in the About dialog and in the Settings dialog's Library section is the packaged version; no version string exists anywhere in `ui/`, so the two can never disagree.
- Exactly one place in the codebase defines scrollbar appearance; no component sets `scrollbar-color`, `scrollbar-width` or the WebKit pseudo-elements (asserted: only `html`, `*`, and the WebKit pseudo-element rules declare them).
- Exactly one place defines a tooltip's appearance (`Tooltip.svelte` + tokens); no control draws its own label bubble, and no toolbar control renders visible text.
- The drag region is declared once on the strip with `"deep"` and disabled per control with `"false"`; no component adds another drag region.
- The applied ramp carries a concrete `color-scheme`, so UA-drawn chrome always matches the ramp on screen.
