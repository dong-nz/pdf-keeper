# PDF Keeper — Release Specification v0.0.2

**Status: ON-GOING** (approved by the user 2026-11-03, build opened the same day — DR-80; registry status is the authority, this line is descriptive). Base: `docs/specs/SPEC-v0.0.1.md` (RELEASED, frozen). This spec carries forward everything v0.0.1 released and adds the changes below; unlisted requirements are unchanged. Registry entry: `docs/specs/INDEX.md`.

## 0. Scope and version

UI restructure + polish release (version set by the user, DR-65; the restructure was folded in by DR-69). Adopted from the 2026-11-03 UI review discussion: the A1–A5 polish batch, three user-requested chrome changes, and the sidebarless navigation decided in OQ-14 (DR-68).

**Out of scope for v0.0.2** (raised in the review, not adopted): reading progress / Finished state (needs a page source — candidate for a future release), list-view grouping (Author/Category/Status), Series/Subjects metadata, page-count and last-opened columns. They stay recorded proposals, not requirements.

## 2. Requirements

### Modified

**UI-01 (Layout)** — old text: *"Layout as sketched above: sidebar (library filters + categories), toolbar (search, import, sort, view toggle), virtualized document area with cover thumbnails (FR-16), status bar."*
New text: Layout: toolbar (Browse menu, search, Import, Sort, View menu, active-filter chips, window controls), virtualized document area with cover thumbnails (FR-16), status bar. **No sidebar.** Saved-search behavior, counts and their persistence (FR-11/FR-12 saved views) are unchanged; category filtering changes only as stated under FR-02 (DR-82) — the controls move (UI-09/UI-10) and several categories may be active at once.

**FR-02 (Categories — filter semantics)** — old text (SPEC-v0.0.1-categories.md): *"Create, rename, delete categories. A document may belong to zero or more categories (many-to-many). Sidebar lists categories with live document counts; selecting a category filters the library. Deleting a category detaches it from documents but never deletes the documents."*
New text: Create, rename, delete categories. A document may belong to zero or more categories (many-to-many). **Any number of categories may be active as a filter at once; the active set selects the union — a document matches when it carries at least one active category. The category set combines with a saved search (All / Favorites / Missing) and with the search terms as before: (category A OR category B) AND favorites/missing AND terms.** Category lists show live document counts; deleting a category detaches it from documents but never deletes the documents. The active set persists like the last filter. Category CRUD is unchanged.

**FR-10 (Import — auto-assignment)** — old text (SPEC-v0.0.1-importing-pdfs.md): *"… Importing while a category is selected auto-assigns the imported documents to it; with no category selected, nothing is assigned."*
New text: … Importing while **one or more** categories are active auto-assigns the imported documents to **every active category** (one assignment set per import, in the same transaction); with no category active, nothing is assigned. Duplicate handling, the import pipeline and the progress reporting are unchanged (FR-11, FR-15).

**FR-13 (Sorting)** — old text: *"Sort library by title, date added, file size (asc/desc); default title A→Z; favorites always pinned first."*
New text: Sort library by title, date added, file size (asc/desc); **a secondary sort key may be set ("Then by…": none by default, then title / date added / file size); ordering is total: primary key, then secondary key, then id as final tiebreaker so order is deterministic**. Default title A→Z with no secondary key; favorites always pinned first. The secondary choice persists like the primary.

### Defect fix (no requirement change)

**D1 — activation.** The released spec defines activation as *double-click on a row/card, `Enter` on the focused row, or the row's Open action* (SPEC-v0.0.1-opening-and-deleting.md §UI, FR-08). The shipped code opens on **single** click (Shift/Ctrl-click selects). v0.0.2 aligns the code with the released text: single click focuses/selects the row or card; double-click, `Enter`, and the Open action activate (open); Shift/Ctrl-click selection is unchanged. Recorded as DR-66 — the deviation was never recorded at implementation time.

## 3. Technical design (v0.0.2)

### 3.1 Window chrome (UI-07)

- `src-tauri/tauri.conf.json`: `"decorations": false`. Capabilities (`capabilities/default.json`): add `core:window:allow-minimize`, `core:window:allow-toggle-maximize`, `core:window:allow-close` (deny-by-default kept).
- `ui/src/components/WindowControls.svelte` (new): three icon-buttons (`aria-label` Minimize / Maximize / Close) calling `getCurrentWindow().minimize() / toggleMaximize() / close()`; mounted at the toolbar's right end. Maximize button mirrors window state (`onResized` → data-maximized for the restore glyph swap).
- Toolbar root carries `data-tauri-drag-region`; interactive children (search input, buttons, menus) are not drag regions.
- App grid becomes `"toolbar" / "main" / "status"` rows (see §3.6; the `side` column disappears with the sidebar). The toolbar row keeps its shipped `--toolbar-height` (52px), which hosts the controls; the control buttons are 44×52 hit areas.
- Risks accepted: Windows Snap layouts / hover-maximize are lost with `decorations: false` (mitigated by the maximize button); `Alt+F4` and taskbar behavior are OS-side and unchanged.

### 3.2 Browse menu and filter chips (UI-09)

- `Sidebar.svelte` is **deleted** (component, rail CSS, `--side-rail` token, `sidebar.*` i18n keys). Its local `collapsed` state disappears with it — no settings migration (it was never persisted).
- **Filter model (FR-02 as modified, DR-82).** `FilterState.category_id: number | null` becomes `category_ids: number[]` (ascending, deduplicated — the order is normalized so the same set always encodes identically). `api.QueryArgs.categoryId` becomes `categoryIds: number[]`. Commands: `library_search` / `library_ids` take `category_ids: Vec<i64>`; `library_import_paths` / `library_import_folder` take `category_ids: Vec<i64>` and assign each imported document to **every** active category in the same transaction (FR-10 as modified). `Query.category_ids: Vec<i64>`; the WHERE clause becomes one `AND EXISTS (SELECT 1 FROM document_categories dc WHERE dc.document_id = d.id AND dc.category_id IN (…bound placeholders…))` — an empty set emits no clause, so "no categories" is the same SQL as before, and the union semantics live in the `IN` list. Mode filters (`favorite = 1` / `missing = 1`) and the search matcher AND with it exactly as shipped. Counts (`get_counts`) stay library-wide — unchanged.
- **`last_filter` encoding.** Grammar: `mode` [`&cats=` id (`,` id)*] where `mode ∈ {all, favorites, missing}`. A category set and a mode may now be active together, so the two are encoded separately instead of one token. A value written by v0.0.1 (`cat:5`) is read as `all&cats=5` — an existing saved filter is never silently dropped by the upgrade. Validation stays on both sides of the boundary (`service::is_valid_filter` and the UI encoder/decoder), and unknown category ids are dropped on restore exactly as the single-id case did.
- `BrowseMenu.svelte` (new): bits-ui Menu at the toolbar's left end. Saved-search items clear the mode part of the filter (All also clears the category set); the Categories submenu renders `library.categories` as checkable items whose checked state is membership in `filter.category_ids`, toggling one id per selection. *Manage categories…* opens UI-10.
- `FilterChips.svelte` (new): renders from `library.filter` (single source of truth): a chip per active category id (name + ×) and one for Favorites/Missing mode; × removes that one filter and leaves the rest active. Chips are buttons: focusable, Enter removes, Esc closes menus as usual.
- `ui/src/App.svelte` grid: remove the `side` area and `<Sidebar/>`; toolbar row hosts BrowseMenu, search, Import, Sort, View, chips, AppMenu, WindowControls.
- Persistence: `settings.svelte.ts` keeps persisting `last_filter` under the new grammar; on startup the restored filter renders as chips. No DB schema change (the settings table is key-value); `view`/`sort`/`dir` keys untouched.
- i18n: new `browse.*`, `chips.*`, `categoriesDialog.*` keys; the coverage test also fails on any orphan `sidebar.*` key.

### 3.3 Categories manager (UI-10)

- `CategoriesDialog.svelte` (new): bits-ui Dialog (focus-trapped, Esc closes — same wrapper rules as every other dialog: explicit `bind:open`, the RenameCategoryDialog pattern). Lists categories with live counts (same `$computed` sources the sidebar used); inline *New category* input (Enter submits; duplicate-name inline error — same backend error path); per-row Rename / Delete open the existing `RenameCategoryDialog` / `DeleteCategoryDialog` unchanged.
- Backend commands unchanged (`app_add_category`, `app_rename_category`, `app_delete_category`, `app_list_categories`).

### 3.4 View menu (UI-08)

- `ViewToggle.svelte` is removed; `ViewMenu.svelte` (new) uses the bits-ui Menu primitive with the global menu chrome (base.css, DR-56 layering). Items: List, Grid (check marks), separator, Columns row: `Auto` item + `−` / count / `+` buttons (manual counts clamped 2–10). The counter always shows the count **in effect** — the Auto count while Auto — and `−` / `+` step from it, disabled only at the 2 / 10 bounds (DR-86). `ui/src/lib/state/layout.svelte.ts` (new) owns the measured document-area width and the Auto count derived from it; `DocumentArea` measures into it and reads it instead of keeping a local width.
- `ui/src/lib/virtual.ts` (DR-83): `gridLayout(containerWidth, override: number | null, cardWidth = 220, gap = 12)` returns `{ columns, cardWidth }`. Auto (`override === null`) reproduces the shipped `gridColumns` computation exactly at the shipped 220 px card width. A manual count wins as far as the window allows: `columns = min(count, what fits at the 140 px floor)`, `cardWidth = clamp(floor((containerWidth − (columns − 1) × gap) / columns), 140, 220)`. Unit tests extend the existing windowing tests: Auto unchanged, override wins, floor and ceiling, a count below Auto keeps the 220 px card.
- `DocumentGrid.svelte`: blocks become `display: grid; grid-template-columns: repeat(columns, {cardWidth}px)` (left-aligned, trailing slack as today); `DocumentCard.svelte` takes `cardWidth` (default 220) and sizes the cover `cardWidth − 2` wide at the shipped 218:309 ratio; `--card-height` and `--cell-height` are untouched, so `window()` and `nearEnd()` keep their shipped constants.
- Settings: new keys `grid_columns` (`"auto" | int`) and `sort_secondary` added to the existing settings round-trip (`settings.svelte.ts`, `app_get_settings`/`app_set_setting` — no schema change; the settings table is key-value).

### 3.5 Secondary sort (FR-13)

- `SortMenu.svelte`: a separator plus a **"Then by…"** section with four items — *None* (default, checked when unset), *Title*, *Date added*, *File size* — each with the check mark on the active one. **No direction control of its own: the secondary follows the primary's asc/desc** (DR-81). Settings: `sort` stays the primary key, `dir` the single direction, new key `sort_secondary` (`"none" | "title" | "date_added" | "size"`); existing keys `view`, `sort`, `dir`, `last_filter` unchanged.
- `src-tauri/src/library/query.rs`: `Query` gains `sort_secondary: Option<SortKey>`; `order_clause` emits `ORDER BY d.favorite DESC, <primary> <dir>, <secondary> <same dir>, d.id ASC` — secondary `None` → `ORDER BY d.favorite DESC, <primary> <dir>, d.id ASC`, byte-identical to the shipped v0.0.1 clause. `parse_sort_secondary` whitelists `"title" | "date_added" | "size"`, anything else (including `"none"`) → `None`. Favorites pinning unchanged. SQL-level unit tests: primary+secondary ordering, tie determinism through the secondary, `None` reproduces the shipped order exactly.

### 3.6 Metadata display (UI-06)

- `DocumentRow.svelte`: title cell becomes a stacked block — `.title-line` (1 line, ellipsis, `title` tooltip), `.author-line` (secondary color, only when `doc.author` non-empty), `.notes-line` (tertiary, ellipsized, only when non-empty). Row height is data-determined (DR-85): `--row-height` 48 px stays the base, each rendered metadata line adds `--row-line` 18 px (48 / 66 / 84 px), and the row's own height is set from the same rule the windowing uses — never by content growth alone. The §5.3.7 column-drop rules keep their order (filename drops below 1100px, size/date below 900px); author/notes live inside the title cell, which never gives way.
- `ui/src/lib/virtual.ts` (DR-85): `window(scrollTop, viewportHeight, offsets, overscan)` and `nearEnd(scrollTop, viewportHeight, offsets, near)` read a prefix-offset array (`offsets[i]` = top of item `i`, `offsets[count]` = total height); `rowOffsets(rows)` / `rowHeight(doc)` produce it for the list, `uniformOffsets(count, height)` for the grid's uniform blocks. Binary search finds the window bounds; the padding/total-height invariant the shipped tests assert is unchanged.
- `DocumentCard.svelte`: `.title` clamps to 2 lines (`-webkit-line-clamp: 2`) with full-text tooltip; `.author-line` under it when non-empty.
- No backend change: `author` and `notes` are already in `documents_list` DTOs (`db/mod.rs` schema, `library/service.rs`).
- Data note for the user guide: author/notes visibility is display-only; extraction/editing behavior is unchanged (FR-05/FR-06).

### 3.7 Activation fix (D1)

- `DocumentRow.svelte` / `DocumentCard.svelte`: `onclick` → row/card focus only; `ondblclick` → `library.open(doc.id)`. `Enter` and the Open action already match the spec and stay. Shift/Ctrl/Win-click selection unchanged.
- `library.svelte.ts`: no new command; open path unchanged (`app_open_document`).
- Smoke harness: `flowOpen` and every flow that opens a document switches to a W3C double pointer-up sequence; a new assertion proves single click does **not** open (regression guard for D1).

### 3.8 Custom scrollbars (UI-11)

- `design-tokens.css`: two new tokens per ramp — light `--scrollbar-thumb: #c9cfd8`, `--scrollbar-track: transparent`; dark `--scrollbar-thumb: #3b424e`, `--scrollbar-track: transparent` (the ramps' `--border-strong` values: the bar reads as chrome, never as content).
- `base.css`, one rule set and nothing else (corrected in the build, DR-87 — the draft claimed both properties are inherited): `html { color-scheme: light dark; scrollbar-color: var(--scrollbar-thumb) var(--scrollbar-track) }` and `* { scrollbar-width: thin }`. `scrollbar-color` **is** inherited; `scrollbar-width` **is not** — measured in the running app with the width declared on `html` only, every container except the root drew the 15 px platform bar in the token color. Declaring the width for every element keeps it a single definition: no component may define its own scrollbar colors or width (R1.6).
- Older-WebKit fallback (macOS target, R8.1; `scrollbar-color` support is newer there): `::-webkit-scrollbar { width: 11px; height: 11px }`, `::-webkit-scrollbar-track { background: var(--scrollbar-track) }`, `::-webkit-scrollbar-thumb { background: var(--scrollbar-thumb); border-radius: 6px; min-height: 40px }`. Engines that support the standard properties ignore the pseudo-elements, so the two spellings never compete — one style written for two engines, not a second implementation path.
- Excluded deliberately: thumb hover/recolor-on-scroll. With the inherited-property route it needs per-surface `:hover` rules (and `html:hover` is always true), so it is left out of the requirement rather than half-implemented.
- Recorded consequence: the document scroller's reserved width drops 15 px → 10 px (measured in the verified build), so `containerWidth` grows 5 px and a grid column count can shift by one at boundary window widths. `virtual.ts` measures `clientWidth` (already scrollbar-excluded), so windowing stays honest and AC-10's Auto computation is unchanged (re-measured in the verified build: Auto still derives 5 columns at 1280 px). No `scrollbar-gutter` reservation (user decision, DR-73).
- Verification: new smoke flow `flowScrollbars` measures `offsetWidth − clientWidth` and the computed `scrollbar-color` for each surface that actually scrolls (the document area with the whole library, the categories manager list), asserts every one of them reserves the same thin gutter and draws the token colors, reads the declared `color-scheme`, and lists which stylesheet rules declare scrollbars (only the shared ones — a component override fails the run); the theme the OS reports is measured live and the other ramp is verified in the loaded stylesheet, plus the real-app observation (R6.4).

### 3.9 App menu and About dialog (UI-12)

- `src-tauri/src/commands.rs`: `pub struct AboutDto { name: String, version: String }` (`serde::Serialize`, camelCase on the wire) and `#[tauri::command] pub fn app_about(app: AppHandle) -> Result<AboutDto, AppErrorPayload>` returning `app.package_info()`'s name and version. No service module and no business logic — it reads Tauri's own metadata (R1.2 thin wrapper). Registered in `lib.rs`'s `generate_handler![…]`; `ui/src/api.ts` adds `"app_about"` to `COMMANDS` plus an `appAbout()` wrapper — the existing pairing test (`lib.rs`: router list vs `api.ts` `COMMANDS`) guards the two sides against drift.
- One version source: `src-tauri/tauri.conf.json`, read at runtime. `ui/package.json`'s `version` field is not read by the app and MUST NOT be used for display (R1.6 — no second source for the same fact). Measured in the current build: `plugin:app|version` → `0.0.1` and `plugin:app|name` → `PDF Keeper` already answer under the granted `core:default`, while `plugin:app|get_tauri_version` is refused ("not allowed. Command not found") — but those built-ins are outside the whitelisted command set (R1.3), so the app uses its own `app_about`. No capability change (R1.5).
- `ui/src/components/AppMenu.svelte` (new): the `SortMenu.svelte` pattern — `DropdownMenu.Root`, `.control` trigger with `<Icon name="info">` and `aria-label` `menu.app`, `.menu` content with the single item `menu.about`. Mounted in `Toolbar.svelte` after the View menu and before `WindowControls` (§3.1/§3.2 toolbar order), so the app menu is the last app control and the window controls stay at the very end.
- `ui/src/components/AboutDialog.svelte` (new): through `Modal.svelte` only (width `--modal-width-small`), title `about.title`; body shows the application name and a `about.version` labelled value from `appAbout()`. Read-only: no inputs, no actions, no persistence, no settings or DB access.
- `ui/src/components/icons.ts`: one new `info` glyph path. i18n: `menu.app`, `menu.about`, `about.title`, `about.name`, `about.version` — the i18n coverage test extends to the new keys and still fails on orphan keys.
- Verification: new smoke flow `flowAbout` — reach the app menu by keyboard from the toolbar, open it, select About with Enter, assert the dialog is open with focus trapped, read the version text, and compare it with the value `app_about` returns through the real command boundary (no version literal in the frontend); Esc closes it. Plus the real-app observation (R6.4).
