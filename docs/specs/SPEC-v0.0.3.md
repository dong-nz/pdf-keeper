# PDF Keeper — Release Specification v0.0.3

**Status: ON-GOING** (approved by the user 2026-11-04 and the build go given the same turn; `docs/specs/INDEX.md` is the authority for this status). Base: `docs/specs/SPEC-v0.0.2.md` (RELEASED, frozen), which carries forward `docs/specs/SPEC-v0.0.1.md` (RELEASED, frozen). This spec carries forward everything v0.0.2 released and adds the changes below; **unlisted requirements are unchanged.** Registry entry: `docs/specs/INDEX.md`.

## 0. Scope and version

**Version set by the user 2026-11-04 (DR-91): the next feature release is v0.0.3**, on the 0.0.x line, following v0.0.1 and v0.0.2.

**Product scope (agreed 2026-11-04, DR-93…DR-99): two batches on the shipped UI.** (1) Minimalism: icon-only toolbar controls with tooltips (UI-13); the import control moved inside the search field (UI-14); the filter chips removed (UI-09 MODIFIED); the search placeholder naming the current scope (UI-16); category badges removed from rows and cards (UI-03 MODIFIED); a conditional status bar (UI-15); uniform control rhythm across the row; and the window-drag defect fixed (D2). (2) Navigation and density rework: the View menu absorbs sorting and the Sort control disappears (UI-08 MODIFIED); the app menu disappears and a **Settings menu with a Settings dialog and a System/Light/Dark theme override** takes its place (UI-12 MODIFIED, UI-17 ADDED); a **Select mode** toolbar toggle (UI-18 ADDED); the selection checkbox and the persistent star removed, the Details action re-iconed (UI-03); taller list rows and container-derived grid cards (design §5.3.5/§5.3.7 MODIFIED).

**One Rust-core change, no Tauri command, no data-model and no dependency change:** the `theme` settings key (§3.8) — `SETTINGS_KEYS`, its validation arm, the `get_settings` fallback and `SettingsDto`. `bits-ui` already ships the Tooltip primitive the design uses (verified against the installed 2.20.3), and every behavior stays behind the existing commands. Unchanged by this release: import behavior (FR-10/FR-11, including the shipped file drag-and-drop), search semantics (FR-03), categories (FR-02), counts and rescan behavior (FR-15), covers, relink, favorites, sorting behavior (FR-13). Out of scope: cross-platform packaging (DR-92).

**Out of scope for v0.0.3 (decided by the user 2026-11-04, DR-92):** cross-platform packaging (Linux `.deb`/AppImage, macOS `.dmg`) and CI. `tauri.conf.json` keeps `targets: ["nsis", "msi"]`. Accepted consequence: **NFR-04 (Linux and macOS support) is not met by the shipped artifacts** — the app runs there in dev, but no installer exists for those platforms. The gap is stated in the v0.0.3 release notes as a known limitation and stays a candidate for its own later release; it is also one of the items DR-47 named for the future app-updates release, which needs a signed per-platform artifact.

**Carried-forward proposals, not requirements** (from SPEC-v0.0.2 §0 and the v0.0.2 release notes): reading progress / Finished state, list-view grouping (Author/Category/Status), Series/Subjects metadata, page-count and last-opened columns, window geometry persistence (deferred by OQ-11/DR-44), matched-term highlighting (deferred by SPEC-v0.0.1 §5.3.6). They remain undecided; nothing here adopts them.

The Details action renders the **`info` glyph** (already present in `ui/src/components/icons.ts`); `tag` remains the category glyph in the picker, the bulk bar and the context menu. **UI-08 (View menu)** — old text (as released by SPEC-v0.0.2): *"**View menu.** The toolbar's two view-toggle buttons are replaced by one **View** menu: List and Grid items (current mode checked), a separator, and a Columns control — `Auto` (width-computed, the shipped default) or a manual column count (2–10) adjusted with − / +. FR-13 is untouched: the same whitelisted keys, the same single ORDER clause, the same `sort` / `dir` / `sort_secondary` persistence. Only the entry point moves. The card width the Columns control produces is no longer clamped to 220 px (§3.10).

**UI-12 (App menu)** — old text (as released by SPEC-v0.0.2): *"**App menu and About dialog.** The toolbar gains an **app menu** at its right end, immediately left of the window controls: a control button with an info icon and an accessible label, opening a menu whose only item is **About PDF Keeper…**. It opens a dialog through the shared modal wrapper (focus-trapped, closes on Esc, close button) showing the application name and its version, read from the packaged application at runtime — the version is never written in the frontend. No other menu item, no links, no runtime or platform details, nothing persisted."*
New text: The app menu control is removed and `AppMenu.svelte` is deleted with it (R7.4). The About dialog is unchanged in every respect — same shared modal wrapper, same focus trap and Esc, same runtime-read name and version, no links, nothing persisted — and is reached from the Settings menu (UI-17) as *About PDF Keeper…*. The window controls stay at the toolbar's right end.

**Design rules §5.3.5 and §5.3.7** — old text (SPEC-v0.0.1.md): *§5.3.5: "List: `itemSize = 48`. Grid: columns are derived from the container width (`columns = floor((width + gap) / (220 + 12))`, `itemSize` = one row block of cards = 401), computed once per resize, not per item."* · *§5.3.7: "Dark and light ramps are authored independently — dark is not an inversion of light. `prefers-color-scheme` selects the ramp; there is no in-app theme override."*
New text — §5.3.5: List `itemSize = 64` (a row with metadata lines still adds 18 px per line). Grid: the column **count** is chosen first (Auto as today, or the manual 2–10 count clamped to what fits at the 140 px floor); the **card width is then derived** from the container — `floor((width − (columns − 1) × gap) / columns)`, **capped at 320 px** — and the grid is centered in the leftover space; `itemSize` is one row block computed from that card width (cover = width × 311/220 plus the card's text block). Still computed once per resize, never per item, so offsets remain computable from the index alone — the purity rule of §5.3.5 is preserved because the derived numbers are fixed for the duration of a resize. New text — §5.3.7: both ramps stay as authored, no token value changes. The ramp is selected by a setting: `system` (the default) keeps `prefers-color-scheme` as the rule; `light` and `dark` override it through a `data-theme` attribute on the document root, which out-specifies the media block.

### Modified — selection semantics (D1's alignment, FR-08 unchanged)

Old text (SPEC-v0.0.2 §2, D1): *"v0.0.2 aligns the code with the released text: single click focuses/selects the row or card; double-click, `Enter`, and the Open action activate (open); Shift/Ctrl-click selection is unchanged."*
New text: **FR-08's activation rule is not touched** — double-click, `Enter` and the Open action remain the only paths that open a document. What changes is what a plain click does with the selection: in the default browse mode a click **focuses only** and leaves the selection untouched; in Select mode (UI-18) a click toggles it. `Shift`/`Ctrl`-click ranges and `Space` on the focused row are unchanged in both modes. Reason: with the checkbox removed (UI-03) a click that always selected would make selection invisible-by-accident — a user browsing the list would build a selection set they never asked for, which is the behavior the user asked the mode to remove. The user's own wording was "select mode off = click opens"; the agreed form keeps double-click activation (their choice on OQ-23) and makes "off" mean "a click does not select", which is the nearest behavior to that wording that does not MODIFY FR-08.

### Defect fix (no requirement change)

**D2 — window drag region.** The released text (SPEC-v0.0.2 UI-07: *"The window is draggable from the toolbar strip (not from controls, inputs or menus)"*) is not delivered. The app's only drag-region attribute is the bare one on `<header class="toolbar">` (`ui/src/components/Toolbar.svelte:17`), and Tauri's `isDragRegion` grants a bare attribute only when the mousedown target **is** that element (`attr === '' → el === composedPath[0]`); clickable children are rejected outright and non-clickable children fail the identity test. Only the header's own padding and the gaps between controls respond, so in practice the window cannot be moved and double-click-to-maximize is unreachable. Root cause and fix in §3.1; the requirement text is unchanged, as the shipped text was correct.

## 3. Technical design

All of it is frontend (`ui/`); no Rust, no command, no schema change. Design stays in this parent (the v0.0.2 precedent — one coherent batch, no feature specs).

### 3.1 Window drag region (D2)

Verified mechanism, from the installed Tauri (`tauri-2.12.5/src/window/scripts/drag.js`, `isDragRegion`, which walks `e.composedPath()` on `mousedown`): a bare or `"true"` `data-tauri-drag-region` triggers only when `el === composedPath[0]`; `"deep"` triggers for any descendant; `"false"` disables; and **any clickable element** (`A, BUTTON, INPUT, SELECT, TEXTAREA, LABEL, SUMMARY`, a non-`-1` `tabindex`, `contenteditable`, or an interactive `role`) **without the attribute stops the walk immediately**.

Fix: `<header class="toolbar" data-tauri-drag-region="deep">`, and `data-tauri-drag-region="false"` on each control wrapper — `BrowseMenu`, the Select-mode toggle (§3.9), `ViewMenu`, `SettingsMenu` (§3.8), `SearchBox` (including the import control inside it), `WindowControls`. `SortMenu` and `AppMenu` are no longer in the row at all (§3.7, §3.8), so they carry nothing. Effect: the whole strip (spacer, gaps, padding) drags and double-click toggles maximize/restore, while controls, the input and menu triggers behave exactly as controls — which is what UI-07 already requires. The explicit `"false"` on non-clickable wrappers is what keeps a click on the *padding around* a control from dragging the window.

No new capability, permission or configuration: the same internal `plugin:window|start_dragging` / `plugin:window|internal_toggle_maximize` calls the shipped window buttons already use. `tauri.conf.json` is untouched (`decorations: false` stays).

### 3.2 Toolbar and the search field (UI-13, UI-14)

- `Toolbar.svelte`: composition becomes **Browse menu · search field (with the import control) · spacer · Select-mode toggle · View menu (view mode, columns, sorting) · Settings menu · window controls** — six controls where the shipped row has seven. `.toolbar-actions` and its separators are deleted; the row uses one gap value and `--control-height` for every control. `--toolbar-height` stays 52 (§5.3.7 metrics unchanged); the row gets shorter in item count, not in height.
- `FilterChips.svelte` is deleted; `library.filter` remains the single source of truth (§5.3.4 unchanged).
- `BrowseMenu.svelte` and `ViewMenu.svelte`: their triggers drop the `<span>` label and keep `aria-label`; each trigger is wrapped by the tooltip wrapper (§3.6). The existing i18n keys `browse.menu` and `toolbar.view` supply both the accessible name and the tooltip text. `toolbar.sort` and `menu.app` lose their controls and are deleted from the catalog with them — `i18n/coverage.test.ts` fails on an unused key, so the removal is enforced by the existing test rather than by a note. New keys are required for the new controls and the new dialog: the Select-mode toggle, the Settings menu and its items (*Settings…*, *About PDF Keeper…* — the About strings already exist), the theme states (`theme.system`, `theme.light`, `theme.dark`), the dialog's section and row labels, and the Browse menu's count/Rescan text (UI-09). Every one is catalog text (R4.1), none is a literal in a component.
- `ImportButton.svelte` is deleted. The plus control lives inside `SearchBox.svelte`, after a 1 px `--border-strong` divider at the field's trailing end; the clear button and the plus share that slot (clear while `text !== ""`, plus otherwise). Both call the existing `importFlow` functions (`pickFilesAndImport`, `pickFolderAndImport`). The `plus` path already exists in `components/icons.ts` (line 25) — no new icon.
- The plus opens a two-item menu — *Import files…* and *Import folder…* — reusing the shipped menu chrome and the existing `pickFilesAndImport` / `pickFolderAndImport` paths (DR-96). Rejected in the decision: moving *Import folder…* to the app menu (would MODIFY UI-12's agreed "No other menu item" — the mootness of that objection is recorded in DR-99, since the app menu is now removed by the user's own request) and a right-click on the plus (an invisible affordance). `Ctrl+I` and the drag-and-drop path are unchanged.
- Icon-only controls carry no state on the icon (UI-13): the Browse menu shows checked items for the active filter, the View menu the active mode, column setting **and sort**, the Settings menu the active theme as its checked item. The Select-mode toggle is the one control whose state must be visible on the control itself — a mode with no visible state is unusable — and it shows it as a pressed control (`aria-pressed`, `--accent-quiet` fill), never as text (§3.9).

### 3.3 Status bar (UI-15)

`StatusBar.svelte`: left = `<span class="doc-count">` with `formatCount(counts.total)`, always rendered, `--text-tertiary`, 12 px, `tabular-nums`. The `counts` group, its three chips and the Rescan button are deleted. The missing-file warning renders only when `counts.missing > 0`. `ProgressBar` stays job-gated; the result count stays filter-gated. The `contentinfo` landmark, the `status_updated` payload and the FR-15 invariant are unchanged; the frontend still never computes or caches a count.

`BrowseMenu.svelte` gains what the status bar loses: *All documents*, *Favorites* and *Missing* carry their counts as trailing text (tabular-nums, `--text-tertiary`, from the same `status_updated` payload the store already holds), and a *Rescan files* item joins the action section that already carries *Manage categories…* — disabled while a job runs, calling the same `library.rescan` path with the same confirmation-free behavior (FR-15). Menu item counts are live: they update with every `status_updated`, exactly as the status-bar chips did.

### 3.4 Rows and cards (UI-03)

`CategoryChips.svelte` is removed from `DocumentRow.svelte` and `DocumentCard.svelte`; the component has no other caller (verified: those two files only) and is deleted with it (R7.4 — no dead component stays). `DetailsModal` and `CategoryPickerModal` render membership through their own code and are unaffected. `DocumentDto.categories` stays exactly as it is (DR-51): Details, the picker and the assignment flows read it, and a per-window extra query would be a second data path (R1.6).

**Metrics change — this is the release that changes them** (the earlier draft of this section said they would not; the user asked for a taller row and a bigger cover, so they do). `ROW_HEIGHT` 48 → **64** in `lib/virtual.ts` and `--row-height` with it; the cover becomes **45×64**, the A4 ratio at that height — the shipped 34×48 cover grows with the row rather than keeping its old size. `ROW_LINE` stays 18, so a row carrying two metadata lines is 64 + 36; `rowHeight(doc)` and the offsets builder keep their shape, only the base constant changes. `virtual.test.ts`'s list cases are re-derived from 64: the assertions (bounded mount counts, `padTop`/`padBottom` correctness, `totalHeight`) are the same claims, with the new numbers.

The selection checkbox element is removed from `DocumentRow.svelte` and the checkbox overlay from `DocumentCard.svelte`; `StarButton.svelte` stays the same component and is now called from the actions line. `RowActions.svelte`'s shown set becomes `favorite, details, delete` (`ROW_ACTION_IDS` in `lib/actions.ts` changes with it) and keeps the existing hover / `:focus-within` display rule — the loss of a permanent favorite marker is stated in UI-03's text, not hidden. The details action's icon changes from `tag` to the `info` path already in `components/icons.ts` (`lib/actions.ts:48`); `lib/actions.ts`'s category and bulk entries keep `tag`. `DocumentRow`'s keyboard contract (roving tabindex, `Space` toggles selection, `Enter` opens) is unchanged — only the visual affordance disappears, which is why UI-18 exists. The checkbox's catalog keys (`row.select`, `row.selectRangeHint`) lose their only users and are deleted with it; `i18n/coverage.test.ts` fails on an unused key, so the deletion is enforced by the existing suite. The range hint moves to the Select-mode toggle's tooltip text.

### 3.5 Search placeholder (UI-16)

`SearchBox.svelte` derives the placeholder from `library.filter` and `library.counts` (already in the store from `status_updated`) through `t()` with new catalog keys: `search.placeholder.all`, `.category`, `.categories`, `.favorites`, `.missing`, `.favoritesCategories`, plus a fixed `search.label` for the input's `aria-label` (today the accessible name duplicates the placeholder text and would shift with state — it must not). Numbers go through `formatCount` and the existing `Intl.PluralRules` path; the R4.1 catalog rule stays compiler-enforced and `i18n/coverage.test.ts` keeps flagging any unused key. The placeholder is display-only: it never enters the query, and typing hides it natively.

### 3.6 Tooltip wrapper (§5.3.1 MODIFIED)

New wrapper `ui/src/components/Tooltip.svelte` over the kit's Tooltip primitive — **verified present in the installed `bits-ui@2.20.3`** (`dist/bits/tooltip/exports.d.ts` exports `Root`, `Trigger`, `Content`, `ContentStatic`, `Arrow`, `Provider`, `Portal`). Contrast with DR-52, where the kit shipped no Toast and `ToastStack` was hand-rolled: here the primitive exists, so the wrapper is the correct form — behavior from the kit, every visual from tokens.

§5.3.1's wrapper list — old text: *"each primitive is wrapped once in `components/` (`ContextMenu.svelte`, `Modal.svelte`, `ToastStack.svelte`, `StarButton.svelte`, `SortMenu.svelte`), and no other component imports the kit (R1.6)"* — gains `Tooltip.svelte` and loses `SortMenu.svelte`, whose items move into `ViewMenu.svelte` (§3.7); the rule itself is unchanged, and `ToastStack` stays hand-rolled per DR-52.

Visuals: 12 px text, `--surface-0` on `--surface-1`-adjacent chrome with a 1 px `--border-hairline`, radius 6, no shadow (a tooltip is not an overlay in the elevation sense of §5.3.7); one `Tooltip.Provider` mounted once in `App.svelte` with a short open delay; positioning by the kit's tether. Hover and keyboard focus produce the same tooltip (R4.4).

Stated before coding, per the DR-45 precedent: nesting the kit's `Tooltip.Trigger` around another kit primitive's trigger (the menu triggers) must compose on one element. If that composition fails in the installed version, the deviation is raised under Rule 7 before any code is written — the fallback is a wrapper element around the control, which changes no behavior.

### 3.7 View menu and the removal of the Sort control (UI-08)

`ViewMenu.svelte` gains the two sections `SortMenu.svelte` renders today, through the kit's submenu primitive on the same wrapper the View menu already uses; `SortMenu.svelte` is deleted with the toolbar control (R7.4) and its item list — already derived from the whitelisted sort keys in `lib/actions.ts` and the settings store — moves with it. `Toolbar.svelte` loses the Sort control and the app control and gains the Select toggle and the Settings menu.

Nothing in the backend moves: `library_search`'s single ORDER builder, `parse_sort_secondary`, the `sort` / `dir` / `sort_secondary` keys and their batched persistence are untouched (FR-13 unchanged, R1.6 keeps one mechanism). The shipped keyboard shortcuts are unaffected because they act on the store, not on the control that displays the value. The new controls carry `data-tauri-drag-region="false"` like every other control, so §3.1's drag region is not re-opened by adding them.

Risk stated before coding (Rule 7): a menu that holds both view mode and sorting is one control fewer, and sorting is the item a user is most likely to look for by the word "Sort". The mitigation is inside the menu — the section headers *Sort by* and *Then by* are the shipped strings, and the accessible name of the toolbar control stays the catalog's "View" label. If the real-app check shows sorting is hard to find, the fix is the control's label, not a second control; that deviation would be raised before any code is written.

### 3.8 Settings menu, Settings dialog and the theme key (UI-17)

**Frontend.** New `SettingsMenu.svelte` (kit Menu wrapper) at the toolbar's right end; `AppMenu.svelte` is deleted and its About item moves here. New `SettingsDialog.svelte` through the existing `Modal.svelte` wrapper, 560 px like Details, two sections. Appearance binds to the existing stores (`settings.svelte.ts` for theme/view/columns) — the dialog is a second entry point to the same state, never a copy of it, and writes go through the existing batched flush (AC-09's fix), not a new debouncer. Library section reads `library.counts` (from `status_updated` only, FR-15's invariant) and the application name and version through the same app-plugin calls the About dialog already makes.

**Rust core (the only backend change in this release).** `src-tauri/src/library/mod.rs`: `SETTINGS_KEYS` gains `theme` (7 entries). `src-tauri/src/library/service.rs`: `set_setting` gains the validation arm `matches!(value, "system" | "light" | "dark")`, and `get_settings` reads the key with a `system` fallback for a corrupt stored value, exactly as `grid_columns` and `sort_secondary` already do; `SettingsDto` gains the field. No new Tauri command — `app_get_settings` / `app_set_setting` already carry it (R1.2 unchanged, no capability change). `cargo test` cases: a valid theme round-trips; an invalid value is rejected as `AppError::Validation`; a corrupt stored value reads back as `system`.

**Applying the ramp** (as implemented — the drafted spelling duplicated the dark palette, corrected by DR-101). `design-tokens.css` holds the light ramp in `:root` and the dark ramp in **one** block, now selected by `:root[data-theme="dark"]`; there is no `@media (prefers-color-scheme: dark)` block for colors any more. `data-theme` on the document root carries a **concrete** value (`light` or `dark`), never the stored `system`: a new `ui/src/lib/theme.ts` owns the resolution — `applyTheme(choice)` maps `system` through `matchMedia("(prefers-color-scheme: dark)")`, and `onSystemThemeChange` lets `App.svelte` keep an OS flip live while the choice is `system`. `main.ts` calls `applyTheme("system")` synchronously before `mount()` so the first paint still follows the OS with no stored value (NFR-07's first-paint rule unchanged); `App.svelte` re-applies the stored choice as soon as `app_get_settings` resolves, so a stored `light` never flashes dark. `color-scheme` moves with the ramp: `:root` declares `light`, the dark block declares `dark` (base.css no longer declares it), so UA-drawn chrome follows the theme the app is *showing*, not the OS. Why this form: the drafted mechanism needed two blocks carrying the dark values (the media rule for the `system` case, an attribute rule for an explicit `dark` against a light OS) — 20 duplicated color declarations, against R7.2 and the file's own single-source rule.

**Not in this release, recorded so it is not invented later.** Language switching (the user named it as a future item): the i18n layer exists (`ui/src/lib/i18n/`, catalog-compiled, `i18n/coverage.test.ts`), and the dialog's Appearance section is where such a control would go — but a language switch is a capability of its own (a second catalog, a persisted key, a locale test matrix) and is not part of v0.0.3. The library's on-disk location is also not shown: exposing it needs a new whitelisted command or a new capability grant, neither agreed here; if it is wanted it enters as its own item with its own Decision Log entry.

### 3.9 Select mode (UI-18)

The mode lives in `lib/state/layout.svelte.ts` — the existing owner of non-persisted UI state (the measured document-area width, DR-86) — as a single boolean, deliberately absent from `settings.svelte.ts` and from `SETTINGS_KEYS`: a mode that persisted would be a setting, and the user's decision is that it is not. `DocumentRow.svelte` / `DocumentCard.svelte` branch their click handler on it: off → focus only (the roving-tabindex focus the row already takes), on → `library.toggleSelection(id, event.shiftKey)` as today. `ondblclick`, `Enter`, the Open action, `Space`, `Ctrl`-click and the range behavior are shared by both modes and are not re-implemented (R1.6). `BulkBar.svelte` is untouched: it already appears whenever a selection exists and already carries *Select all matching*, set-categories, favorite/unfavorite and delete. One new glyph (a selection square) is added to `components/icons.ts` — an internal path set, no dependency change (no Decision Log entry needed: RULES R8 governs dependencies, not icon paths).

Consequence recorded honestly: in the default mode a click no longer selects, so the only pointer path to a selection is `Ctrl`/`Shift`-click — the mode is what makes plain bulk work reachable, and AC-30 is written to catch the case where the two modes drift apart.

### 3.10 Grid geometry (design §5.3.5 MODIFIED)

`lib/virtual.ts::gridLayout` keeps its shape and loses its cap: `cardWidth = min(320, max(MIN_CARD_WIDTH, floor((containerWidth − (columns − 1) * gap) / columns)))`, with `columns` derived exactly as today (Auto from 232 px pitch, or the manual 2–10 count clamped to what fits at the 140 px floor). A new pure helper `cardHeight(cardWidth)` returns the card's height — `10 + coverHeight(cardWidth) + 70`, where `coverHeight` is the shipped inner-cover ratio (a `cardWidth − 2` inner cover at 218:309, DR-83) and the `70` is the card's fixed text block; at the shipped 220 px card this reproduces the shipped 389 px exactly, which is the anchor the derivation must not move. `cellHeight(cardWidth) = cardHeight + CARD_GAP` is the derived value passed to `window()` as `itemSize` (`CELL_HEIGHT` is deleted); `DocumentGrid.svelte` sets `grid-template-columns: repeat({columns}, {cardWidth}px)` and the block height from the same numbers, centered by `justify-content: center` in the leftover width. The card metrics stop being constants in `design-tokens.css` (`--card-width`, `--card-cover-height`, `--card-height`, `--cell-height` are deleted; `--card-gap` stays): the numbers come from one pure function and are passed down as inline custom properties, so no token would be a second source of truth (R4.5 governs where a *fixed* value lives, and these are no longer fixed).

Auto mode is no longer a 220 px card with slack: at 1280 px it yields 5 columns of ~247 px instead of 5 of 220 px. A manual count of 2 at 1280 px yields 2 cards of the 320 px cap, centered, with the remaining space as margin — the cap is what keeps a cover from becoming a poster. `virtual.test.ts` gains the derived-height cases and the cap boundary (the count at which the cap starts to bind, and the 140 px floor where the count stops being honored); the existing bounded-mount and offset assertions are re-run against the derived numbers rather than against 401.
