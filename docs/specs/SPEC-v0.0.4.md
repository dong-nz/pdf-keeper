**Status: PROPOSED** (drafted 2026-11-04; `docs/specs/INDEX.md` is the authority for this status). ## 0. Scope and version

**Version set by the user 2026-11-04 (DR-107): the next feature release is v0.0.4**, on the 0.0.x line, following v0.0.1 → v0.0.2 → v0.0.3 (DR-91). v0.1.0 stays reserved for the app-updates release (DR-47/DR-48); OQ-16's carried question is answered here — v0.0.4 is the release after v0.0.3.

**Product scope direction (user, 2026-11-04, DR-107): "bug fixing and enhance ui".** A quality release on the surface v0.0.3 shipped: fix what is wrong or half-done in the running app, and improve the existing UI. No new capability areas, no new data model, no new dependency unless a Decision Log entry is approved first (AGENTS §2).

**Out of scope for v0.0.4 (all carried, unchanged):** cross-platform packaging and CI (Linux `.deb`/AppImage, macOS `.dmg` — deferred by DR-92, still a release of its own); automatic app updates and the v0.1.0 slot (DR-47/DR-48); reading progress / "Finished" state; list-view grouping by author/category/status; Series/Subjects metadata; page-count and last-opened columns; language switching (out of scope again; **Vietnamese** is named as the target of the later capability release, DR-114). Each stays a candidate for a later release, none is adopted here.

**ID policy for this draft.** `FR-17` onward and the `app-updates` slug remain reserved by DR-47, so this release consumes **no `FR-` or `NFR-` ID**: defects are recorded as `D3`, `D4`, … and UI changes as `UI-19`+. New acceptance criteria start at `AC-32`, new questions at `OQ-26`, new decision records at `DR-107`. If a fix turns out to need a data-model or capability change, coding stops and the reservation is reopened under RULES R9.3 before any code is written.

**Verification baseline (measured, not assumed).** The v0.0.3 build at commit `22131c3` passes its full gate: `cargo fmt --check` and `clippy -D warnings` clean, 49 Rust tests, the Vitest unit scope, and the 30-flow real-app smoke run with nothing skipped. **No defect is open in the registry** — D1 (DR-66), D2 (DR-95/DR-103), the settings-flush defect (DR-104/DR-105) and the dialog-Escape defect (DR-106) were each found and re-verified fixed. The defect batch of this release therefore comes from two sources only: what the user observes in the running app, and the quality gaps inventorited in §5 — each of which is a measured fact about the shipped code, not a guess.

## 2. Requirements

Every requirement of v0.0.3 — and through it v0.0.2 and v0.0.1 — stays authoritative except where modified below. `FR-17` onward and the `app-updates` slug remain reserved by DR-47; this release consumes no `FR-` or `NFR-` ID. ### Modified

**FR-16 (Cover thumbnails)** — old text (as released by `SPEC-v0.0.1-covers.md`, AGREED DR-16/DR-17): *"Cover thumbnails. Every document displays a first-page cover in list rows and grid cards. Covers are generated at import, regenerated by Rescan when the file changed or the cover is absent, cached in the app-data directory **keyed by path+size+mtime**, and removed when the library entry is removed. Unrenderable pages fall back to a generic PDF glyph."*
New text: unchanged in every respect **except** the cache identity: covers are cached keyed by **path + size + mtime + the renderer's current target width**. The width is part of the identity so that changing how the app renders can never leave a stale, smaller image being served for a document that already has an entry. Consequence, recorded rather than hidden: changing the target width re-keys every entry, so the first start after this release re-renders the whole library in the background queue while the old files are swept — the UI stays usable throughout (NFR-02, R5.1) and covers fill in progressively. `RULES.md` R5.2 is amended to match (DR-114).

**UI-17 (Settings dialog, Library section)** — old text (as released, AGREED DR-99), affected clause: *"**Library** — document, favorites and missing counts from `status_updated` only, and the application name and version read at runtime."*
New text: **Library** — the same counts, the same runtime-read name and version, **plus the directory the application writes its data into** (UI-21). Read-only: no path picker, no move, nothing persisted. The Appearance section, the theme key and every other control are untouched.

**Design rule §3.10 (grid geometry)** — old text (as released by `SPEC-v0.0.3.md` §3.10): *"…`cardWidth = min(320, max(MIN_CARD_WIDTH, floor((containerWidth − (columns − 1) * gap) / columns)))` … A new pure helper `cardHeight(cardWidth)` returns the card's height — **`10 + coverHeight(cardWidth) + 70`**, where `coverHeight` is the shipped inner-cover ratio (a `cardWidth − 2` inner cover at 218:309 …)"*, and the shipped rule it produced (`DocumentGrid.svelte:89-92`): *"No horizontal inset: `layout.areaWidth` is the scroller's own content width, and the derived cards fill exactly that."*
New text: `cardHeight(cardWidth) = coverHeight(cardWidth) + 70` — the 10 px cover padding is gone because the cover now occupies the card's inner box from its top edge (D6); `coverHeight` and the 218:309 ratio are unchanged, and so is the cover's rendered width, `cardWidth − 2`. `containerWidth` is no longer the scroller's raw `clientWidth`: it is **`clientWidth − 2 × 12`** (UI-19), the content width the gutter leaves. The row/card containers carry the 12 px inset; the windowing math is given the reduced width, so the last column still cannot overflow and no horizontal scrollbar can appear. Still derived once per resize, never per item (§5.3.5's purity rule preserved).

## 3. Technical design

Build order per AGENTS stage 3: Rust core (§3.5, §3.10) → Tauri commands (§3.10) → Svelte UI (§3.1–3.4, §3.6–3.9). Nothing here touches the schema, `DocumentDto`, the search pipeline, the settings keys or the capabilities file.

### 3.1 D3 — icon centring (`ui/src/lib/base.css`)

`.icon-button` is the class that owns the square box (`base.css:145-152`: `display:inline-grid; place-items:center; width/height:var(--control-height)`); it is the only place the correction belongs. Add `padding: 0` to it. With `box-sizing: border-box` the content box becomes 30×30 inside the 1 px border and `place-items: center` centres the 16 px glyph — dx 0, dy 0, the same result the row/card icon buttons already measure.

`.control` (`base.css:94-106`, `padding: 0 10px`, 1 px border, `min-height: var(--control-height)`) is not touched: text controls keep their inset, and the toolbar's hover/active chrome (`.control:hover`, `[aria-pressed]`) is unchanged. `.icon-button` keeps the border it inherits from the pairing, so the visible box is the same 32×32 with the same radius.

No component changes. The four pairings (`BrowseMenu.svelte:54`, `ViewMenu.svelte:64`, `SettingsMenu.svelte:38`, `Toolbar.svelte:35`, `WindowControls.svelte`) stay as they are — the pairing is what gives them the menu-trigger chrome, and it is not the defect.

### 3.2 D4 — the actions line as one control type (`base.css`, `StarButton.svelte`, `RowActions.svelte`)

**Box.** `.star` (`base.css:389-410`) changes from `width/height: 20px` to `width/height: var(--control-height)`, and takes the same hover/focus treatment `.icon-button` has (`background: var(--surface-2)` on hover, the shared focus ring, `border-radius: var(--radius-control)`, `color: var(--text-primary)`), keeping `[aria-checked="true"] → color: var(--accent)`. `.star-thumb` stays `place-items:center`; the glyph size becomes the 16 px the other two actions use. Result: three 32×32 boxes on one 64 px row, centres on the row's centre line.

**Tooltip.** `RowActions.svelte` wraps each action in the app's existing `Tooltip` wrapper (`components/Tooltip.svelte`, kit `Tooltip.Root/Trigger` with the `control` snippet, `side="bottom" sideOffset={6}`) and drops the `title` attributes. The wrapper merges the kit trigger props onto the same element, so one element carries both behaviors — the pattern the toolbar already uses. `StarButton.svelte` accepts those merged props and applies them to `Switch.Root`, which keeps `role="switch"`, `aria-checked`, `aria-label` and the Space/Enter behavior from the kit (R4.4, DR-45): the primitive is not replaced (DR-113). The `Tooltip.Provider` already wraps the app (`App.svelte:169`), so no provider is added.

**Layout.** The actions bar narrows from 84 px (32+20+32) to 96 px (3×32) plus the existing gap; `.row-actions` keeps its hover/`focus-within` reveal rule and its `display:none` default (UI-03 as released, OQ-24's accepted consequence unchanged). The card's `.actions-slot` overlay position is unchanged.

### 3.3 D5 — menus bounded and scrollable (`base.css`)

One rule on the shared menu chrome, covering `DropdownMenu.Content`, `SubContent` and the context menu (all carry `.menu`):

```css
.menu {
  max-height: calc(100vh - 2 * var(--menu-edge));
  overflow-y: auto;
  overscroll-behavior: contain;
}
```

`--menu-edge` is a new design token in `design-tokens.css` set to the gap the overlay already keeps from the window edge (12 px), so the bound is the same number the positioner uses rather than a second guess. Height is bounded before the positioner measures the panel, so the panel fits; the kit's own collision handling then keeps it inside the viewport instead of shifting an oversized panel past both edges.

Nothing else moves: no positioning code exists to change (`OverlayAnchor.svelte` is the overlay-lifecycle counter only, DR-45), the menu item styles, submenu behaviour, the multi-select category behaviour (DR-82) and the Esc/overlay counter are untouched. Keyboard reachability is verified, not assumed: the smoke flow walks a 30-category submenu with `ArrowDown`/`End` and asserts the last item is reached and focused (the kit scrolls the highlighted item into view).

### 3.4 D6 — the cover inside the card (`DocumentCard.svelte`, `Cover.svelte`, `virtual.ts`)

**Geometry.** `.cover-wrap` loses its padding (`padding: 10px 10px 0` → none): the cover box starts at the card's inner top-left and its inline size `cardWidth − 2` is exactly the inner width the card's 1 px border leaves. `coverW = cardWidth - 2` and `coverHeight(cardWidth)` stay as they are — the cover's rendered size does not change, only its position, so the picture that was overflowing by 8.6 px now ends flush with the border.

**Card height.** `cardHeight(cardWidth)` drops the priced padding: `coverHeight(cardWidth) + CARD_TEXT_BLOCK` (70, unchanged: two clamped title lines, author line, meta line, bottom padding). `cellHeight` follows it. `CARD_TEXT_BLOCK`'s derivation comment is rewritten to the new formula (it is currently `389 - 10 - 309`, which prices the padding that no longer exists). `virtual.test.ts`'s card-height and row-block cases are re-derived at the new numbers; the width matrix, the 320 cap and the 140 floor cases are unchanged.

**Chrome.** Inside `.cover-wrap`, the cover's own 1 px border is dropped and its radius becomes the card's inner radius (`var(--radius-control) − 1px`), so the card shows one border and one continuous rounded corner instead of two nested ones. The list row's cover keeps its current border and radius — the row has no card border to merge with, and its 45×64 cover is unchanged.

**Why not shrink the cover instead** (the alternative the user declined, DR-112): sizing the cover to `cardWidth − 22` would keep the 10 px inset but change the rendered pixels, the 218:309 derivation and every card-height number, for a visual result the card border already achieves.

### 3.5 D7 — 640 px covers and a cache identity that carries the width (`src-tauri/src/covers/mod.rs`)

```rust
/// The renderer's target width. Part of the cache identity (FR-16 as modified,
/// R5.2): changing it re-keys every entry instead of serving a smaller stored
/// image forever. 640 px covers a 320 CSS px card at 2× device scaling.
pub const RENDER_TARGET_WIDTH: u32 = 640;
const RENDER_TARGET_HEIGHT: u32 = (RENDER_TARGET_WIDTH as u64 * 309 / 218) as u32; // 905
```

`render_cover` uses `PdfRenderConfig::new().set_target_width(RENDER_TARGET_WIDTH).set_maximum_height(RENDER_TARGET_HEIGHT)` — the same A4 ratio as today, scaled up, so a portrait page yields 640×905 and a wider page is height-capped exactly as the 220/311 pair caps today.

`cache_key(path, size, mtime)` becomes `cache_key(path, size, mtime, width: u32)` and `cache_path` passes `RENDER_TARGET_WIDTH`; every caller (`query::map_row`, `enqueue_missing_covers`, `sweep_orphans`, the tests) threads it the same way. The width is hashed with the same `DefaultHasher` sequence as the other three parts.

**No migration code.** The first start after this change is handled by what already exists: `sweep_orphans` deletes every cached PNG whose key no longer matches a row (all 220 px files), and `enqueue_missing_covers` re-enqueues every document because the new key is absent — the queue renders them in the background with its existing progress events (R5.1, NFR-02). Consequence recorded for the release notes: on a 10 017-document library the covers reappear progressively over minutes, with placeholders meanwhile (R5.3's glyph and the shimmer, not a broken image).

**Measured baseline** for the cost claim: the current cache holds 10 016 PNGs, 23.5 MB total, 2.2 KB each at 220×285. At 640 px the same fixtures are ~8.4× the pixels; the disk growth and the re-render time are measured at verification, not asserted here.

### 3.6 D8 — Relink on the row (`ui/src/lib/actions.ts`, `RowActions.svelte`)

`ROW_ACTION_IDS` gains `"relink"`. Nothing else in the definition changes: `relink` already carries `applies: doc.missing` (`actions.ts:59-62`), `RowActions` already filters `applies` per target, and the row's rendering order follows `documentActions`' order — so the actions line shows the same sequence the context menu shows, for missing documents only. The same component renders the card's `.actions-slot`, so both views get it (R4.7). No new command: the action runs the shipped relink path (the file picker, then `library_relink_document`).

### 3.7 D9 — scrollbars (`base.css`)

The standard properties stay authoritative — they are what governs in this runtime (measured: `scrollbar-width: thin`, `scrollbar-color` applied, 10 px reserved gutter) and they are what UI-11's released design asks for. The fallback block keeps its colours and width, and gains the one declaration it never had:

```css
/* The fallback draws its own arrow buttons unless they are removed; the app
   has no arrow buttons anywhere (UI-11 as extended by DR-115). */
::-webkit-scrollbar-button {
  display: none;
  width: 0;
  height: 0;
}
```

That is the whole change: it reaches every scroll container because the pseudo-element rules are global, exactly as the existing `-track`/`-thumb` rules are, and nothing is added to a component (UI-11's "one rule set" rule preserved).

Recorded honestly: in this environment the block is inert, so the change is measured to alter nothing here (gutter 10 → 10, byte-identical screenshots). It removes the only construct in the app that can draw arrow buttons, which is the mechanism the review describes. If the arrows are still visible in the user's app after this lands, the mechanism is elsewhere and **OQ-30 is reopened** rather than the item being called fixed — AC-38 is verified in the running app for that reason.

### 3.8 UI-19 — the gutter (`virtual.ts`, `DocumentArea.svelte`, the containers)

`virtual.ts` exports `CONTENT_GUTTER = 12`, mirroring a new `--content-gutter` token in `design-tokens.css` (the same lockstep rule `ROW_HEIGHT`/`CARD_GAP` follow, and the same single source for CSS and math).

`DocumentArea.svelte:118` changes from `layout.setAreaWidth(el.clientWidth)` to `layout.setAreaWidth(el.clientWidth - 2 * CONTENT_GUTTER)` — one change point, so every consumer (`gridLayout`, the row width, the block offsets) receives the content width. `clientWidth` includes padding, which is exactly why the inset cannot be applied as padding on the scroller alone while the raw width is still handed to the math.

The containers take the inset visually: `.rows` and `.grid` get `padding-inline: var(--content-gutter)` (the absolute-positioned window keeps its `inset: 0` block, so `padTop`/`padBottom` and the mounted-node bound are unaffected — NFR-01 unchanged), and the list's rows keep `width: 100%` of the padded content box. The grid's column derivation now sees the reduced width, so the 320 cap and the "no horizontal scrollbar" property are preserved with the same arithmetic.

Out of this item's scope, stated so it is not drifted into: the toolbar, the status bar, the bulk bar and the dialogs keep their current insets.

### 3.9 UI-20 — labels (`ui/src/lib/i18n/en.ts`, `i18n/coverage.test.ts`)

The ellipsis is removed from every value in the audit list (`en.ts:14,28,29,36,65,77,98,109-111,135,153,154,184,206`) and from the prose string that names the menu item (`:162`). The three progress values stay and stay in the `job.*` group (`Importing…`, `Checking files…`, `Generating covers…`). `en.ts` is the only catalog (`NFR-05`), so no other file carries label text; `plural-count.test.ts` and `coverage.test.ts` keep their existing checks.

`coverage.test.ts` gains the mechanical rule that keeps this from drifting back: every value in the catalog is asserted to contain no trailing "…" unless its key is under the progress group. The test is the acceptance criterion (AC-40), not a one-off edit — a future label added with an ellipsis fails the suite.

Accessible names, tooltip texts and the `aria-label`s the actions line uses are the same strings, so D4 and UI-20 land on one set of labels: the star, Details, Delete and Relink tooltips read "Favorite", "Details", "Delete", "Relink".

### 3.10 UI-21 — the library location (`src-tauri/src/commands.rs`, `ui/src/api.ts`, `SettingsDialog.svelte`)

**Rust.** One command, same shape as `app_about` (`commands.rs:342-347`), which already reads runtime facts and returns a DTO:

```rust
#[tauri::command]
pub fn app_data_dir(app: AppHandle) -> Result<String, AppErrorPayload> {
    app.path().app_data_dir()
        .map(|dir| dir.to_string_lossy().into_owned())
        .map_err(AppErrorPayload::from)
}
```

The path is the one the app itself uses: `lib.rs:160-163` resolves `app.path().app_data_dir()`, creates it, and puts `library.db` (`db::open`) and `covers/` inside it. The command reads the same source rather than a stored copy, so what is displayed is what the app writes to. No new state, no new capability grant (R1.5 untouched), no business logic in the command body (R1.2).

**Frontend.** `app_data_dir` joins `COMMANDS` in `api.ts` with a typed `appDataDir(): Promise<string>`; the existing Rust integration test that asserts set equality between the router's list and `COMMANDS` (spec §5.3.3) is the guard. `SettingsDialog.svelte`'s Library section gains one `info-row`: label *Location*, value the returned path, selectable text in the existing `.info-list` styling, fetched once when the dialog opens. No control, no write path, nothing persisted (R1.4).
