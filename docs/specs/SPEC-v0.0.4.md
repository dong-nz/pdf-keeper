## 0. Scope and version

**Version set by the user 2026-11-04 (DR-107): the next feature release is v0.0.4**, on the 0.0.x line, following v0.0.1 → v0.0.2 → v0.0.3 (DR-91). v0.1.0 stays reserved for the app-updates release (DR-47/DR-48); OQ-16's carried question is answered here — v0.0.4 is the release after v0.0.3.

**Product scope direction (user, 2026-11-04, DR-107): "bug fixing and enhance ui".** A quality release on the surface v0.0.3 shipped: fix what is wrong or half-done in the running app, and improve the existing UI. No new capability areas, no new data model, no new dependency unless a Decision Log entry is approved first (AGENTS §2).

**Out of scope for v0.0.4 (all carried, unchanged):** cross-platform packaging and CI (Linux `.deb`/AppImage, macOS `.dmg` — deferred by DR-92, still a release of its own); automatic app updates and the v0.1.0 slot (DR-47/DR-48); reading progress / "Finished" state; list-view grouping by author/category/status; Series/Subjects metadata; page-count and last-opened columns; language switching (out of scope again; **Vietnamese** is named as the target of the later capability release, DR-114). Each stays a candidate for a later release, none is adopted here.

**ID policy for this draft.** `FR-17` onward and the `app-updates` slug remain reserved by DR-47, so this release consumes **no `FR-` or `NFR-` ID**: defects are recorded as `D3`, `D4`, … and UI changes as `UI-19`+. New acceptance criteria start at `AC-32`, new questions at `OQ-26`, new decision records at `DR-107`. If a fix turns out to need a data-model or capability change, coding stops and the reservation is reopened under RULES R9.3 before any code is written.

**Verification baseline (measured, not assumed).** The v0.0.3 build at commit `22131c3` passes its full gate: `cargo fmt --check` and `clippy -D warnings` clean, 49 Rust tests, the Vitest unit scope, and the 30-flow real-app smoke run with nothing skipped. **No defect is open in the registry** — D1 (DR-66), D2 (DR-95/DR-103), the settings-flush defect (DR-104/DR-105) and the dialog-Escape defect (DR-106) were each found and re-verified fixed. The defect batch of this release therefore comes from two sources only: what the user observes in the running app, and the quality gaps inventorited in §5 — each of which is a measured fact about the shipped code, not a guess.

### Modified

**FR-16 (Cover thumbnails)** — old text (as released by `SPEC-v0.0.1-covers.md`, AGREED DR-16/DR-17): *"Cover thumbnails. Every document displays a first-page cover in list rows and grid cards. Covers are generated at import, regenerated by Rescan when the file changed or the cover is absent, cached in the app-data directory **keyed by path+size+mtime**, and removed when the library entry is removed. Unrenderable pages fall back to a generic PDF glyph."*
New text: unchanged in every respect **except** the cache identity: covers are cached keyed by **path + size + mtime + the renderer's current target width**. The width is part of the identity so that changing how the app renders can never leave a stale, smaller image being served for a document that already has an entry. Consequence, recorded rather than hidden: changing the target width re-keys every entry, so the first start after this release re-renders the whole library in the background queue while the old files are swept — the UI stays usable throughout (NFR-02, R5.1) and covers fill in progressively. `RULES.md` R5.2 is amended to match (DR-114).

**UI-17 (Settings dialog, Library section)** — old text (as released, AGREED DR-99), affected clause: *"**Library** — document, favorites and missing counts from `status_updated` only, and the application name and version read at runtime."*
New text: **Library** — the same counts, the same runtime-read name and version, **plus the directory the application writes its data into** (UI-21). Read-only: no path picker, no move, nothing persisted. The Appearance section, the theme key and every other control are untouched.

**Missing-flag presentation (`SPEC-v0.0.1-missing-files-relinking.md` §Design, as migrated to `docs/release/technical-specs/`)** — old text: *"MissingBadge.svelte: a `--warning` chip labeled "Missing" in rows and an overlay badge on card covers. The title stays readable and the tooltip shows the stored path — a missing entry is kept visible, not hidden or dimmed away (FR-12)."*
New text: the row carries the `alert-triangle` glyph and the label as plain text in the corrected warning color (D11) — no ground, no pill; the card overlay keeps a filled badge with a warning-tinted ground and a radius at half the badge's height. The readable title, the stored-path tooltip and the "kept visible, not hidden or dimmed away" rule are unchanged. The shipped row and card render exactly the chip the old text describes (measured, M13) — this is a deliberate change of the released design wording, decided by the user 2026-11-05 (DR-116), not a drift correction: the row's treatment becomes the plain-text one the status surfaces already use.

**Design rule §3.10 (grid geometry)** — old text (as released by `SPEC-v0.0.3.md` §3.10): *"…`cardWidth = min(320, max(MIN_CARD_WIDTH, floor((containerWidth − (columns − 1) * gap) / columns)))` … A new pure helper `cardHeight(cardWidth)` returns the card's height — **`10 + coverHeight(cardWidth) + 70`**, where `coverHeight` is the shipped inner-cover ratio (a `cardWidth − 2` inner cover at 218:309 …)"*, and the shipped rule it produced (`DocumentGrid.svelte:89-92`): *"No horizontal inset: `layout.areaWidth` is the scroller's own content width, and the derived cards fill exactly that."*
New text: `cardHeight(cardWidth) = coverHeight(cardWidth) + 70` — the 10 px cover padding is gone because the cover now occupies the card's inner box from its top edge (D6); `coverHeight` and the 218:309 ratio are unchanged, and so is the cover's rendered width, `cardWidth − 2`. `containerWidth` is no longer the scroller's raw `clientWidth`: it is **`clientWidth − 2 × 12`** (UI-19), the content width the gutter leaves. The row/card containers carry the 12 px inset; the windowing math is given the reduced width, so the last column still cannot overflow and no horizontal scrollbar can appear. Still derived once per resize, never per item (§5.3.5's purity rule preserved).

## 3. Technical design

Build order per AGENTS stage 3: Rust core (§3.5, §3.10) → Tauri commands (§3.10) → Svelte UI (§3.1–3.4, §3.6–3.9, §3.11–§3.21). Nothing here touches the schema, `DocumentDto`, the search pipeline, the settings keys or the capabilities file.

### 3.1 D3 — icon centring (`ui/src/lib/base.css`)

`.icon-button` is the class that owns the square box (`base.css:145-152`: `display:inline-grid; place-items:center; width/height:var(--control-height)`); it is the only place the correction belongs. Add `padding: 0` to it. With `box-sizing: border-box` the content box becomes 30×30 inside the 1 px border and `place-items: center` centres the 16 px glyph — dx 0, dy 0, the same result the row/card icon buttons already measure.

`.control` (`base.css:94-106`, `padding: 0 10px`, 1 px border, `min-height: var(--control-height)`) is not touched: text controls keep their inset, and the toolbar's hover/active chrome (`.control:hover`, `[aria-pressed]`) is unchanged. `.icon-button` keeps the border it inherits from the pairing, so the visible box is the same 32×32 with the same radius.

No component changes. The four pairings (`BrowseMenu.svelte:54`, `ViewMenu.svelte:64`, `SettingsMenu.svelte:38`, `Toolbar.svelte:35`, `WindowControls.svelte`) stay as they are — the pairing is what gives them the menu-trigger chrome, and it is not the defect.

### 3.2 D4 — the actions line as one control type (`base.css`, `StarButton.svelte`, `RowActions.svelte`)

**Box.** `.star` (`base.css:389-410`) changes from `width/height: 20px` to `width/height: var(--control-height)`, and takes the same hover/focus treatment `.icon-button` has (`background: var(--surface-2)` on hover, the shared focus ring, `border-radius: var(--radius-control)`, `color: var(--text-primary)`), keeping `[aria-checked="true"] → color: var(--accent)`. `.star-thumb` stays `place-items:center`; the glyph size becomes the 16 px the other two actions use. ### 3.5 D7 — 640 px covers and a cache identity that carries the width (`src-tauri/src/covers/mod.rs`)

```rust
/// The renderer's target width. Part of the cache identity (FR-16 as modified,
/// R5.2): changing it re-keys every entry instead of serving a smaller stored
/// image forever. 640 px covers a 320 CSS px card at 2× device scaling.
pub const RENDER_TARGET_WIDTH: u32 = 640;
const RENDER_TARGET_HEIGHT: u32 = (RENDER_TARGET_WIDTH as u64 * 309 / 218) as u32; // 905
```

`render_cover` uses `PdfRenderConfig::new().set_target_width(RENDER_TARGET_WIDTH).set_maximum_height(RENDER_TARGET_HEIGHT)` — the same A4 ratio as today, scaled up, so a portrait page yields 640×905 and a wider page is height-capped exactly as the 220/311 pair caps today.

`cache_key(path, size, mtime)` becomes `cache_key(path, size, mtime, width: u32)` and `cache_path` passes `RENDER_TARGET_WIDTH`; every caller (`query::map_row`, `enqueue_missing_covers`, `sweep_orphans`, the tests) threads it the same way. The width is hashed with the same `DefaultHasher` sequence as the other three parts.

**No migration code.** The first start after this change is handled by what already exists: `sweep_orphans` deletes every cached PNG whose key no longer matches a row (all 220 px files), and `enqueue_missing_covers` re-enqueues every document because the new key is absent — the queue renders them in the background with its existing progress events (R5.1, NFR-02). Consequence recorded for the release notes: on a 10 017-document library the covers reappear progressively over minutes, with placeholders meanwhile (R5.3's glyph and the shimmer, not a broken image).

**Measured baseline** for the cost claim: the current cache holds 10 016 PNGs, 23.5 MB total, 2.2 KB each at 220×285. At 640 px the same fixtures are ~8.4× the pixels; the disk growth and the re-render time are measured at verification, not asserted here.
