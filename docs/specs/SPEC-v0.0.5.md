## 3. Technical design

All harness changes live in `scripts/ui-smoke.mjs` and `scripts/make-fixtures.mjs` (product scripts; RULES apply unchanged). No Tauri commands change. No UI code changes.

### 3.1 D13 — two-tier fixtures and suite order (`scripts/make-fixtures.mjs`, `scripts/ui-smoke.mjs`)

Suite shape becomes two sections with an explicit contract:

1. **Functional section** — the app is launched against a library built by importing `fixtures/core`. All flows that act on a handful of rows run here unchanged: categories, context menu, delete, favorites, metadata editor, status bar (with the bounded busy-gate job, §3.1.1), missing/relink, meta column, open, covers (the core library's covers render in ~2 s at measured throughput), display, sorting, columns, gutter, category CRUD, counts, icons, scrollbars, drag region, toolbar, search field, row design, action parity, theme/settings, select mode, about, window chrome, keyboard audit, menu bounds.
2. **Scale section (last)** — import `fixtures/docs` (10 000) through the app's own command: AC-01 (listed + duplicate skip + NFR-02 < 30 s budget asserted), NFR-01 mounted-node bound over 10 000, the AC-39 mounted-bound clause, the width matrix, and the empty/skeleton flow last (its Ctrl+A → "Select all N matching" bulk-extension claim is only observable over the scale corpus — the app pages 500 rows per query, so the control never exists below a 500-document library, DR-136). The section runs its checks and the suite **exits without waiting for the scale cover queue**: no flow after it needs those images, and the next run starts from a wiped library anyway.

Flow-to-tier mapping (the mapping D14 documents for targeted runs): scale tier = `flowImport10k`, `flowVirtualization`, `flowWidthMatrix`, `flowEmptyAndSkeleton` (+ the AC-39 bound clause); everything else = core tier. `flowSearchDebounce` moves to the core tier (its claim is debounce behavior and stale-response suppression, not corpus size).

**3.1.1 Bounded busy-gate job (AC-22/FR-15).** The status-bar quiet-state check and the Rescan-gate check currently use the 10 000-cover queue as "the long-running job" — an implementation accident of the fixture corpus. They instead run a job over the core library: delete its cached cover files **and touch the core fixture files' mtimes**, then run Rescan — a verified fact about `service::rescan` (DR-135) is that deleting covers alone enqueues nothing: rescan enqueues cover jobs only for changed or restored files, so the mtime touch is what makes the job real. The result is a job over all core documents with real progress events, a real busy gate, and a real completion — strictly closer to what the AC describes ("a job the app can actually start"). The "≈ 4 s" first estimate was computed against the 27 covers/s serial queue; after DR-134 the job drains in ~1 s on the pipeline, and the observation is the progress→idle transition itself (progress events plus gate polling at 100 ms), not the duration.

**3.1.2 What must not shrink.** AC-01's 10 000-document import, NFR-01's 10 000-document virtualization measurement, and AC-39's "mounted-node bound … with 10 000 fixtures" clause keep the 10 000 corpus; they are the reason the scale tier exists.

### 3.2 D14 — timing instrumentation and targeted runs (`scripts/ui-smoke.mjs`)

- `runFlow` and the mandatory prefix phases log `[TIME] <name> +<ms>`; the run ends with a summary table (name, ms, total) and the total against the NFR-06 budget. A budget breach is a harness failure (`exit 1`, "budget exceeded: <total> > <limit>") — the budget is asserted, per R6.3. The instrumented throwaway copy used for this spec's measurements is deleted; the shipped harness carries the instrumentation.
- **Named feature-area sets.** The harness carries the §3.2 mapping; `SMOKE_SET=<area-name>` selects exactly that area's flows (implemented on top of the existing `SMOKE_FLOW` mechanism; unknown area names error, as unknown flow names already do). Mid-build verification runs the sets of the areas the change touches; the full suite runs once before the ship gate (AGENTS stage 4 unchanged).
- **Flow self-sufficiency (prerequisite).** No flow may rely on state left by another flow: each establishes its own starting state (clears filters/search/selection, sets its own view mode, creates the entities it needs). Six flows carry such dependencies today (`flowMissingAndRelink`, `flowMenuBounds`, `flowMetaColumn`, `flowSortSecondary`, `flowCategoriesMulti`, `flowEmptyAndSkeleton` — e.g. the first's comment reads "the category filter is still active from the previous flow"); their setup blocks are part of the D13 restructure. Without this, a subset run measures the wrong state and the sets are unreliable.

### 3.3 D15 — build staleness (`scripts/ui-smoke.mjs`)

`buildApp()` is skipped when `target/debug/pdfkeeper.exe` is newer than every input: all files under `src-tauri/` (excluding `target/`), `ui/src/`, `ui/index.html`, `ui/package.json`, `pnpm-lock.yaml`, `tauri.conf.json`, `Cargo.toml`, `Cargo.lock`. Skipped builds log `[BUILD] skipped — inputs unchanged`. Any newer input triggers the normal `tauri build --debug --no-bundle` (the existing rationale for using the Tauri CLI, not bare `cargo build`, is unchanged).

### 3.4 D16 — condition waits (`scripts/ui-smoke.mjs`)

Replace the fixed-sleep inventory: layout re-derivation after resize (400 ms → poll `innerWidth` + first geometry read), column-walk steps (250 ms → poll the menu's reported count), menu open/close (→ poll the panel), dialog open/close (→ poll the surface), restart settle (1 500 ms → poll process exit + immediate session-open retry). Poll interval 100 ms. Kept fixed: the 150 ms search debounce observation windows and the FR-04 "does not jump mid-scroll" window — time is the claim there.

### 3.5 D17 — cover render/encode pipeline (`src-tauri/src/covers/mod.rs`)

Mechanism as decided 2026-11-05 (DR-133 + DR-134; the design was corrected twice during implementation — the measurements are in the Decision Log): the cost is the PNG encoding (35.3 ms/doc), not pdfium rendering (1.2 ms/doc), and the bundled pdfium binary is not safe for concurrent calls (pdfium-render #262; observed suite crashes).

- `start_worker(dir, sink)` becomes `start_pool(dir, sink)`: **one render worker + N PNG-encode workers** (N = `min(4, max(1, num_cpus/2))`; `PDFKEEPER_COVER_WORKERS` overrides N, clamped 1..8 — N = 1 reproduces the v0.0.4 serial behavior). `CoverQueue` keeps its single `mpsc::Sender` and `enqueue` contract.
- Render worker: the only thread that touches pdfium (binds once via the existing `bind_pdfium()`, exactly as released — no new concurrency, no unsafe code, no dependency-feature changes). Per job: the `exists` check, then render to a `DynamicImage`; a failed or impossible render completes the job directly (R5.3 glyph fallback). Successful renders are handed to the encode pool through bounded `sync_channel`s (capacity 2 per worker; the render thread round-robins) — in-flight images ≤ 2N (~2.3 MB each), backpressure blocks the render thread, which is never the bottleneck.
- Encode workers: pure-Rust PNG encode + write (thread-safe), then complete the job. A save failure leaves the glyph as today.
- Completion bookkeeping (shared `ProgressTracker`): the `pending`/`processed` atomics and the throttled progress-event contract (R5.1) are unchanged — a small mutex gate makes the event stream monotonic across workers (every published count is read and stamped under the lock), with the final drain event guaranteed.
- Unchanged: the cache key and path (R5.2, FR-16 as released), the glyph fallback (R5.3), `enqueue_missing_covers` backfill, `sweep_orphans`, the no-worker `test_queue` for deterministic service tests. A job can never be processed twice: one queue, one render worker.
- No sharding (the DR-133 design's device): with one render worker there is nothing to shard.
- The existing queue tests keep passing; new tests per AC-57; the real-app scale section measures the throughput claim.

### 3.6 D18 — width-matrix walk (`scripts/ui-smoke.mjs`)

Adopted 2026-11-05 (OQ-33 → DR-128): at 900/1900 px the matrix measures Auto, manual 2, manual 10 (list and grid, the clamp edges) instead of Auto + 2..10; at 1280 px `flowViewColumns` keeps the full 2..10 walk. `virtual.test.ts` already covers every count at every width derivation and is unchanged.
