## 2. Requirements

### Added

**FR-17 (Built-in PDF reader)** — text: *The app displays and reads PDF documents inside itself: opening a document shows its pages in a dedicated reader window (one window per document — OQ-37 closed, DR-139), navigable to every page and zoomable (fit-width and fixed zoom steps). Reading does not require an external application. Opening a document with the OS default application remains available as an explicit action. A document whose file is missing, or a file that cannot be rendered, never opens silently: the typed error paths of FR-08 apply, and an unrenderable file additionally offers the external-open action.* Scope depth: view + zoom + navigation (OQ-38 closed → DR-139; text selection/search are a later candidate).

**UI-30 (Reader window)** — text: *The reader lives in its own app window: opening a document creates a reader window — default 1000 × 700 CSS px, OS cascade placement, resizable and minimizable, titled with the document name — and opening a document whose reader window already exists focuses that window instead of creating a second one (one window per document). A control strip at the top of the reader window carries, in order: page navigation (previous/next, a `n / N` page field that accepts a page number) and zoom controls (fit-width — the default —, fixed steps 50 / 75 / 100 / 125 / 150 / 200 / 300 %, and − / + between them). The reader window shows no library surface: no toolbar, no menus, no status bar. Pages form a continuous vertical stack with the standard 12 px gap and the standard custom scrollbar (UI-11); only viewport-near pages are mounted (the windowed-rendering rule of UI-04 applies unchanged). The library window is untouched and stays fully interactive while any reader window is open — no busy-gating. `Esc` closes the focused reader window. `PgUp`/`PgDn` scroll, `Home`/`End` jump to the first/last page. The reader window is frameless like the app window (OQ-40 closed 2026-11-06 → DR-140): its own control strip replicates the app's window controls (minimize / maximize / close) and carries the window drag region (UI-07/D2's pattern); the document name is shown in that strip, and the window's title property is set to the filename (task switcher and accessibility).*

**UI-31 (Open paths)** — text: *The document context menu carries, first, **Open** (opens the built-in reader; the `open` glyph changes from the external-link symbol to an in-app reading glyph) and directly below it **Open in external viewer** (the existing OS-default path, keeping the external-link glyph). The row/card hover action line is unchanged (`favorite, details, delete`, plus `relink` for missing files — UI-03/D8). The Details modal's Open control follows the reader path. Labels carry no ellipsis (UI-20).*

**UI-32 (Dracula dark ramp)** — text: *The dark ramp in `design-tokens.css` (`:root[data-theme="dark"]`) is re-authored to the Dracula Classic palette per the §3.6 mapping — surfaces, borders, text roles, semantic colors, selection and hover grounds, scrollbar thumb. The light ramp, the theme control and the `theme` setting key (UI-17) are unchanged; `system` resolution is unchanged (DR-101). The shipped contrast discipline extends to the dark ramp: every text-role token clears 4.5:1 on the exact ground it renders on (the AC-43 measurement method), fill/border/graphics roles clear 3:1. Where a palette base value fails on a ground it is specified to render on, the value is replaced within the Dracula specification itself (its documented brighter variants — the ANSI bright set — or the nearest palette value that clears the threshold), and the substitution is recorded in the Decision Log before the code (R9.1). The text hierarchy uses Foreground at 72 % / 55 % alpha for `--text-secondary` / `--text-tertiary` (OQ-39 closed 2026-11-06 → DR-139).*

**NFR-08 (Reader responsiveness)** — text: *On the reference machine (the NFR calibration machine): opening a document (activation → reader window showing its first page) completes in **≤ 800 ms** — the separate-window model (OQ-37 closed) adds webview creation to the render cost, and the budget states that honestly; a page jump or zoom change (request → new page image visible) completes in **≤ 300 ms** for pages up to 1 000. Asserted by the smoke harness's measured timings (the AC-54 timing table), not by a stopwatch.*

## 3. Technical design

Stages: **Rust core** (`src-tauri/src/pdf/` new module + `covers/` rewiring) → **Tauri commands** (whitelist additions) → **UI** (reader window surface, context menu, dark ramp). No data-model change, no new dependency; the window capability grants are the DR-140 entry specified in §3.3 (R1.5).

### 3.1 `src-tauri/src/pdf/` — the single pdfium owner (RenderService)

The bundled pdfium binary is not safe for concurrent calls (DR-134, pdfium-render #262), and the process-global bind can be taken once. The reader therefore joins the cover pipeline on **one** pdfium owner: a `RenderService` — a dedicated thread that binds pdfium (the existing `bind_candidates()` order moves here unchanged) and serves render requests:

- `RenderRequest::Cover(job)` → decoded image returned on a one-shot channel to the cover pipeline's encode stage (the v0.0.5 encode pool is unchanged);
- `RenderRequest::Page(doc_id, path, page, target_width)` → decoded image returned on a one-shot channel to the calling command thread, which encodes the PNG and writes it to the reader cache (the encode — 96 % of the cost, DR-134 — happens off the service thread, off the UI thread; R3.5).
- The service loop takes page requests ahead of queued cover jobs (interactive work beats background work); cover throughput is unaffected in practice because rendering is 4 % of a cover's cost.
- Missing binary: the service exists but every request resolves to `None` — covers keep the glyph (R5.3), the reader reports the typed error (§3.2); exactly the released graceful-degradation contract.
- `covers/` keeps its queue, its bounded handoff and its `ProgressTracker`; only its render stage becomes a client of the service. The v0.0.5 pipeline tests (exactly-once, monotonic events, glyph fallback) stay green as the regression net (AC-63).

Rendering math: PDF pages are measured in points (72/inch); CSS pixels are 96/inch. `app_pdf_page`'s `target_width` is CSS px; the service renders at `scale = target_width / (width_pt × 4/3)`, bounded to `[0.2, 4.0]` (the zoom bounds of UI-30 plus the 2× device-pixel cap).

### 3.2 Commands (whitelist additions, R1.3)

- `app_open_reader_window(id)` — the activation entry point (UI-31): resolves through `service::open_target` first, so a missing document yields the existing typed `MissingFile` error **before any window exists** (FR-08's error path unchanged); then creates — or focuses, if one labeled `reader-<id>` already exists — the reader WebviewWindow (Rust-side creation: the library frontend needs no window-creation capability, R1.5 preserved). Returns `{ opened: "created" | "focused" }` for the caller's bookkeeping.
- `app_pdf_document(id) -> PdfDocDto { page_count, pages: [{ width_pt, height_pt }] }` — called by the reader window itself; resolves through `service::open_target` (a file deleted after the window opened yields the typed error, which the window renders as its error state); a file that fails to open/render yields a new `AppError::PdfUnopenable` variant → typed payload.
- `app_pdf_page(id, page, target_width) -> String` — `page` is 1-based; `target_width` validated at the boundary to 100..4000 (R1.2). Renders via the service, PNG-encodes, writes to `<app_data>/reader/<doc-key>/<page>-<width>.png`, returns the path (R5.4: paths, never bytes). The reader cache is **session-scoped**: closing a reader window deletes that document's reader directory (Rust window-close handler; the existing startup sweep pattern covers leftovers), and deleting a document removes it with the row, beside the cover-cache cleanup that already exists. No staleness rules: a document's identity is re-resolved on every open, so a changed file re-opens with fresh sizes.
- `app_open_document` stays as the external path (UI-31), unchanged.
- All three new commands join the single Rust whitelist and the typed frontend client (R1.3); the frontend calls nothing else.

### 3.3 Reader windows (`src-tauri/src/` window plumbing + `ui/src/`)

OQ-37 closed 2026-11-06 → DR-139: **one reader window per document** (the user's decision; the agent's in-app-view recommendation is superseded, and its consequences are carried honestly — the NFR-08 open budget, the capability entry below). OQ-40 closed 2026-11-06 → DR-140: **frameless style replicated** in reader windows.

- `app_open_reader_window(id)` (Rust, §3.2) creates or focuses a Tauri `WebviewWindow` labeled `reader-<docId>`, loading the same UI entry with a `?reader=<docId>` route parameter. Creation in Rust keeps R1.5: the library frontend gains no window-creation capability. The label scheme is the one-window-per-document rule.
- `ui/src/main.ts` routes on the parameter: a reader window renders the reader surface only — no toolbar, no menus, no status bar. Each webview is its own JS context, so `state/reader.svelte.ts` is naturally per-window state; no shared UI state crosses windows. Theme: the reader window resolves the stored `theme` through the existing `theme.ts` path (DR-101) — the same ramps, including the Dracula dark ramp (UI-32), apply in every window.
- Window (UI-30, OQ-40-B): `decorations: false` — identical to the released main window — `resizable: true`, default 1000 × 700 CSS px, minimum 640 × 480, OS cascade placement; `title` set to the document filename. The reader window's top chrome reuses the released `WindowControls` component (minimize / maximize / close) and the drag-region pattern (UI-07/D2 — the mechanism fixed per Tauri's `drag.js`, DR-103's grant); the document name is displayed in that strip. The reader control strip (UI-30) sits below it.
- Capabilities (R1.5, **granted by DR-140**, before code): a new entry `reader-windows` in `src-tauri/capabilities/` with `"windows": ["reader-*"]` — glob scoping is confirmed in Tauri's Capability reference ("Windows can be added to a capability by exact name or glob patterns") — and permissions mirroring exactly the chrome set the main window already holds: `core:default` (a window matching no capability has no IPC access at all; the reader must call its commands), `core:window:allow-minimize`, `allow-toggle-maximize`, `allow-close`, `allow-destroy` (DR-105's pattern — Tauri's own close plumbing calls it), `allow-start-dragging` (DR-103's pattern), plus asset reads scoped to `<app_data>/reader/` only (DR-44's pattern, widened from the covers directory to the reader directory *for reader windows only*). The `default` capability on `main` is unchanged; nothing else is granted.
- `ReaderView.svelte` (rendered inside the reader window): page geometry is exact, never measured — CSS size per page = `width_pt × 4/3 × zoom`; the windowed mount follows the `virtual.ts` pattern over the page stack (the mounted-page bound is checked at 1 000 pages, AC-65). Page images request `app_pdf_page` at `display_width × devicePixelRatio` (capped 2×), requested for viewport-near pages only, the current page first (DR-150); **two-stage resolution (MODIFIED at build, measured 2026-11-06, DR-151; preview width MODIFIED again at build, measured 2026-11-06, DR-153)**: when the device target exceeds `min(display width in CSS px, 1 400 px)`, a preview at that width (≈ 150–200 ms to visible on the reference machine) lands first, then the full target, which replaces the preview in place; otherwise the request is single-request as drafted — always the case at `devicePixelRatio` 1 below the cap. The reader scroller sets `overflow-anchor: none` (DR-152): the browser must not adjust the scroll position when a mount swap transiently shifts content above the viewport — the position the app measures is the position it requested. A page shows a neutral placeholder while its request is in flight (the honest-skeleton rule of UI-29). Fit-width default: `zoom = (window content width − 2 × gutter) / (width_pt × 4/3)`, re-derived on window resize (the same resize-derivation path the grid uses). `ReaderControls.svelte` — the strip per UI-30. Zoom steps per UI-30; − / + walk the step list.
- The library window stays fully interactive while reader windows are open — no busy-gating, and the released escape order (SPEC-v0.0.5 §5.2) is untouched (`Esc` closes the focused reader window inside that window). Closing a reader window (close control, `Esc`, or OS) triggers the Rust close handler: cache directory removed (§3.2); nothing in the library window changes. Deleting a document from the library closes its reader window with the row.
- Error surfacing: `PdfUnopenable` → the reader window renders its error state with an **Open in external viewer** action (the typed payload flows through the same command boundary; the toast-action mechanism released for delete-retry/relink, reused, not re-implemented). `MissingFile` cannot reach a reader window — it is checked before creation; the library window's toast + Relink path is unchanged.

### 3.4 Activation and menu (UI-31, FR-08)

`library.open` (the store path behind double-click, `Enter`, Details' Open) calls `app_open_reader_window` (create-or-focus, §3.2). The context menu's `documentActions` list (the single definition behind all action surfaces, R4.7) gains the split: `open` (reader window) and `open_external`. `ROW_ACTION_IDS` is unchanged. The external path keeps its command-boundary behavior (AC-12's call-counting method re-used for AC-68).

### 3.5 Fixtures (`scripts/make-fixtures.mjs`)

The generator gains multi-page documents (generated, never committed binaries — R6.2): the **core tier** adds 5 documents with 12 / 24 / 48 / 96 / 192 pages (deterministic per-page content: the page number drawn in the page's content stream, so a rendered page is distinguishable); the **scale tier** adds one 1 000-page document. Existing single-page fixtures are unchanged (covers keep their corpus). The reader flows read the deterministic page content where a claim needs page identity.

Harness consequence of the window model (MODIFIED at build, measured 2026-11-06, DR-147 — the drafted text assumed "the standard window-handle switch"; it proved unimplementable): reader flows assert across two windows. Under tauri-driver the second WebviewWindow is unreachable — `GET /session/…/windows` answers 404 (tauri-driver does not implement the command), `POST /session/…/window {handle: "reader-<id>"}` answers *no such window* (msedgedriver only sees the webview it attached to), and the WebView2 debug port does not come up for the driver-launched app. The reader flows therefore drive the real binary directly (no driver) with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<port>`, and reach both windows as CDP targets; the CDP helpers mirror the harness's `execute`/`waitForEval`/boundary-capture semantics, and library-side claims (the missing-file toast, "library window stayed interactive") run in the same instance's main window. Unchanged from the draft: reader flows enter `SMOKE_SET` as named sets (AC-54's mechanism) with timing rows (AC-72). Per DR-141, v0.0.6 verification runs only these feature sets (see the §4 scope rule); the NFR-06 budget assertion resumes with the next full-suite run.
