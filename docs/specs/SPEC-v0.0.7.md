**What this release is** (the user's scope decisions of 2026-11-07, DR-172/DR-173/DR-177/DR-178/DR-179):

- **D19 — page-encoding cost** (Rust core): the measured cost of serving a reader page is dominated by PNG encoding (§3.1 M3); it is reduced by tuning the PNG encoder on the existing `image` dependency (OQ-42 closed → DR-178).
- **FR-18 (new) — reader table of contents**: the built-in reader shows a PDF's outline when it has one (OQ-41 closed → DR-177; design §3.5).
- **NFR-09 (new)** — reader scrolling and page serving get measured budgets (the harness rows of §4), locking the verified baselines in as regression guards and bounding the page-serving CPU cost.
- **UI-30 (MODIFIED)** — the reader control strip moves to the window's bottom edge; the window chrome stays at the top (the placement direction the user chose 2026-11-07, DR-172).
- **UI-33 (new)** — the ToC control in the strip and its panel.
- **FR-17 (MODIFIED) + UI-34 (new)** — view modes in the reader control bar: single page / continuous / facing (the user's request of 2026-11-07, DR-179; design §3.6; consecutive pairing and session-only scope decided by the user — OQ-43/OQ-44 closed → DR-180/DR-181).
- **UI-35 (new)** — the light ramp re-authored to the official Dracula **Alucard** palette (the user's request of 2026-11-08, DR-182; the light variant v0.0.6 §0 named as a candidate; design §3.7).
- **UI-03 (MODIFIED)** — grid cards no longer render the document size and date-added line (the user's request of 2026-11-08, DR-183), and their hover action icons render on an opaque ground instead of transparently over card text (the user's request of 2026-11-08, DR-184); card facet design §3.8. Extended by DR-188 (the user's request of 2026-11-08): the list row's cover is enlarged to 51×72 and inset 8 px from the row's separator lines, the row base height 64→88 px (OQ-45 closed as option B → DR-189); design §3.12.
- **UI-36 (new)** - document size is displayed in megabytes wherever the app shows it (the user's request of 2026-11-08, DR-185; design §3.9).
- **UI-19 (MODIFIED)** - the released 12 px content gutter extends vertically: rows and cards keep a 12 px gap to the toolbar's bottom edge instead of starting flush against its hairline (the user's request of 2026-11-08, DR-186; design §3.10).
- **UI-37 (new)** - every tooltip the app shows is rendered by the app's own themed tooltip, on the active ramp's floating-chrome ground; the OS-drawn native-title tooltips that remain today are replaced (the user's request of 2026-11-08, DR-187; design §3.11).
- **UI-17 (MODIFIED)** - the Settings menu's theme submenu becomes one action item that cycles Light -> Dark -> Auto (= follow-the-system); the mode is named Auto and gets a half light / half dark icon (the user's request of 2026-11-08, DR-190; design §3.13). The same item carries the settings dialog's restructure: its Library section is removed - the dialog holds the configuration controls and a Data location section (the user's request of 2026-11-08, DR-191; design §3.14).
- **UI-21 (MODIFIED)** - the data-location row moves into that Data location section and gains one action: an icon that opens the configured path in the OS file manager, through one new whitelisted command; its read-only rules stand (DR-191; design §3.14).

**Out of scope, and why — the corrected baseline (DR-174/DR-175) removed two candidates that the pre-draft discussion had assumed:**

- **Document handle cache — out.** Measured: opening a document through pdfium costs 0.2–2.0 ms and a second page on an open document saves nothing measurable (M3). A cache would add invalidation surface for ≈ 1 ms per page. The service keeps opening each document per request.
- **Scroll-geometry memoization / scroll-event throttling — out.** Measured: a warm back-and-forth scroll costs the same at 192 and 1 000 pages (ScriptDuration 0.043 s vs 0.044 s over 9.6 s), with zero dropped frames and zero long tasks (M2). The per-event geometry recomputation the code does is not a measurable cost; RULES ("do not rewrite working code without a clear reason") says leave it.
- Carried unchanged from v0.0.6 §0: persistent page cache, in-memory page delivery (R5.4), PDF.js, reading progress, text search/selection, and the parked candidates C3–C8. The parked "prefetch/overscan changes" stay parked for the continuous stack — single-mode adjacent-page prefetch enters scope by DR-219 as part of the view-mode behavior, not as an overscan change. The reader ToC is **in** this release (OQ-41 closed → DR-177): `FR-18`, `UI-33`, design §3.5. The Dracula **Alucard** light variant is no longer parked — it is adopted by this release (`UI-35`, design §3.7, DR-182).

## 2. Requirements

### Added

**FR-18 (Reader table of contents)** — text: *The built-in reader shows a document's table of contents when the PDF carries one: the reader's control strip offers a table-of-contents control that opens the document outline as a hierarchical list — entry titles with their target page numbers, nested entries indented by outline depth. Activating an entry jumps the page stack to that page. A document without an outline offers no table-of-contents control.* Scope: view and jump — no current-section highlight, no persisted collapse state, no outline editing. Note: consumes the `FR-18` slot; app-updates re-reserved at `FR-19`+ (DR-177).

**NFR-09 (Reader interaction budgets)** — text: *Reader scrolling and page serving are budgeted on measured cost, asserted by the verification harness's measured rows (AC-73/AC-75), not by a stopwatch. During the scripted cold forward scroll on the multi fixture tier, the app process spends at most the stated per-served-page CPU budget (AC-73), and every page the mount window requested is served by the end of the run. A scripted warm (cached) back-and-forth scroll on the 1 000-page fixture produces no served pages, no app-process CPU, no dropped frames and no main-thread long tasks (AC-75) — the state the corrected baseline measured (M2) and this release must not regress. The NFR-08 open / page-jump / zoom display budgets are unchanged by this release.*

## 3. Technical design

Stages: **Rust core** (`src-tauri/src/pdf/` — the `serve_page` encode stage; `src-tauri/src/pdfmeta/` — outline reading; one new Tauri command, `app_pdf_outline`, a thin wrapper per R1.2) → **Tauri commands** (whitelist + the typed frontend client mirror it; the existing command-set equality test catches any drift) → **UI** (`ui/src/ReaderApp.svelte` layout and `ReaderControls` placement; the ToC control and panel; the view-mode control and the mode-aware layout in `ReaderView`) → **fixtures + harness** (`scripts/make-fixtures.mjs` outline extension; new measured, ToC and view-mode flows). **Build-stage additions (batches DR-229–DR-233): the settings service's event emission (§3.18), the library store's cover-completion re-query (§3.19), the library service's chunked import/rescan pipeline and its progress events (§3.20), and the `TocPanel` structure re-cut with its tooltip (§3.5).** No data-model change, no new crate: the encoder knobs are on the already-pinned `image` 0.25.10 (verified present in the vendored source), and outline reading uses the already-pinned `lopdf` 0.47.

### 3.1 Baseline measurements (the factual base of this spec)

Measured 2026-11-07 on the reference machine against the debug app binary (`src-tauri/target/debug/pdfkeeper.exe` — the same binary the harness runs), with two throwaway tools since deleted (DR-174): `scripts/probe-reader-cpu.mjs` (CDP metrics read at `result.metrics`, process CPU via `Get-Process` over the full process tree including the app process, served pages counted from the reader cache directory) and `src-tauri/tests/bench-encode-tmp.rs` (Rust, pdfium + `image` 0.25.10).

**M1 — scripted cold forward scroll** (100 wheel steps × 400 px @ 120 ms inside the page stack, from the top):

| Fixture | Served pages | app-process CPU | renderer main thread | dropped frames |
|---|---|---|---|---|
| multi-1000 | 32 | **14.52 s** (≈ 453 ms/page) | ScriptDuration 0.071 s, Layout 0.018 s, TaskDuration 0.228 s | 0 / 913 |
| multi-192 | 32 | **14.30 s** (≈ 447 ms/page) | ScriptDuration 0.052 s, Layout 0.019 s, TaskDuration 0.212 s | 0 / 915 |

The app-process cost per page is the same for a 192-page and a 1 000-page document → the cost is per served page, not per document size. The renderer stays responsive throughout: no dropped frames, no long tasks. The user-visible cost is page *availability* (how long a page takes to arrive and to reach full sharpness), not scroll jank.

**M2 — scripted warm back-and-forth scroll** (80 steps × 400 px @ 120 ms over the already-visited range; pages re-enter the mount window from the reader cache):

| Fixture | Served pages | app-process CPU | renderer main thread | dropped frames | long tasks |
|---|---|---|---|---|---|
| multi-1000 | 0 | 0.031 s | ScriptDuration 0.044 s | 0 / 758 | 0 |
| multi-192 | 0 | 0.047 s | ScriptDuration 0.043 s | 0 / 760 | 0 |

Warm scroll is flat in document size and already clean. The WebView2 processes spend 0.7–0.9 s re-decoding cached page images as they re-enter the mount window — the browser's own decode, not app work.

**M3 — per-page cost split** (bench, multi-192 page 1, debug build):

| Stage | @ 966 px | @ 1932 px |
|---|---|---|
| `load_pdf_from_file` (document open) | 2.0 ms | 0.2 ms |
| pdfium raster | 6.2 ms | 4.8 ms |
| PNG encode, current default (`DynamicImage::save`) | **82 ms** (33 KB) | **332 ms** (109 KB) |
| PNG encode, `PngEncoder::new_with_quality(Fast, Sub)` | 52 ms (37 KB) | 207 ms (117 KB) |
| PNG encode, `Uncompressed` + `NoFilter` | 20 ms (4 718 KB) | 80 ms (18 871 KB) |

Summed across the two-stage pattern a page is served at (preview ≈ 966 px + full ≈ 1932 px): ≈ 427 ms — matching M1's measured ≈ 450 ms/page. **Encoding is ≈ 90 % of the per-page app CPU; opening and rastering a document are noise.** The encoder knobs are present in the pinned `image` 0.25.10 (`image::codecs::png::PngEncoder::new_with_quality`, `CompressionType`, `FilterType` — verified against the vendored source).

**M4 — correction of the pre-draft numbers (DR-174).** The numbers quoted in the 2026-11-06/07 discussions (warm-scroll ScriptDuration 1.31 s scaling ~6× with document size; cold-scroll jank 61 dropped frames; per-page cost attributed to document re-opening and O(N) geometry recomputation) came from a probe run with two instrumentation defects: the CDP metrics response was read at the wrong path (the list is nested under `result.metrics` — every metric diff came out zero or stale) and the process tree omitted the app process itself. The corrected re-run above supersedes them. The claims they supported — that warm scroll recomputes geometry expensively, and that re-opening documents is a real cost — did not reproduce: they leave the scope (§0).

### 3.2 Encoding change (D19, `src-tauri/src/pdf/`)

`serve_page` currently renders through the RenderService and then encodes with `image::DynamicImage::save` (the PNG encoder's default balanced compression + adaptive filter). The change replaces that single call with `PngEncoder::new_with_quality(writer, <compression>, <filter>)` — option B, chosen by the user (OQ-42 closed → DR-178). The exact compression/filter values are fixed at build time from measured rows (the bench's `Fast` + `Sub` row — 332 ms → 207 ms at 1 932 px, −38 % — is the expected landing point; the build may measure a better row and take it, recording the choice in the Decision Log); AC-73's measured row proves the result. The cache contract is untouched: same `<reader_dir>/<doc-key>/<page>-<width>.png` key, same PNG format, same two-stage preview/full serving, same interactive-first queue. **Covers stay on the current encoder**: their cache is persistent (bigger files are a real disk cost), the cover pipeline already meets its measured budgets (v0.0.5), and this release does not touch it (AC-74 asserts it stays green). Option C (JPEG pages) was considered and not chosen (DR-178): it would have traded lossy artifacts in a reading app for speed this release does not need; if it is ever revisited it needs its own Decision Log entry before code (R3.4).

### 3.3 Reader layout (UI-30 MODIFIED, `ui/src/ReaderApp.svelte`)

The window grid rows become `var(--toolbar-height) minmax(0, 1fr) auto` and the markup order becomes chrome → `ReaderView` → `ReaderControls`. The controls strip already renders only in the `ready` state — the error state already renders no controls, which the modified requirement now states explicitly. `ReaderControls` itself is unchanged (same content, order, tooltips, page field). `ReaderView` is unchanged: fit-width measures the scroller's content box, whose width does not depend on the row order; the mount rule, request order, and the key map in `ReaderApp` are untouched. The harness's reader flows update their position assertions (strip below the stack, chrome at the top) — the gestures they drive are unchanged (AC-76).

**Name display (amended at build by DR-206, mechanism completed by DR-214).** The chrome's name cell drops the fixed `max-width: 60ch` cap — measured: it ellipsized the 72-character fixture name in a 1000 px window with room to spare. The name flexes to the strip's remaining width (`flex: 1 1 auto; min-width: 0`) and ellipsizes only on real overflow; the app tooltip carries the full name (UI-37/AC-87's claim unchanged), the window title property stays the full filename. The strip is clamped to the window: `grid-template-columns: minmax(0, 1fr)` on the reader grid (DR-214 — measured: the implicit auto column track is sized by the chrome's intrinsic min-content, so the name cell shrank only after the clamp; without it the 693 px strip overflowed even the product's 640 px minimum window). ### 3.4 The measured reader flow (harness)

A new named flow `flowReaderPerformance` joins the `reading-pdfs` area (its lane in the `measure` group, CDP runtime like the other reader flows, own data directory per the AC-60 rule). It runs the M1 scenario against multi-192 and the M2 scenario against multi-1000, and reports the same rows this spec's §3.1 records: app-process CPU (process-tree snapshot around the scenario), served pages (reader cache scan), CDP metrics (`result.metrics`), dropped frames and long tasks (in-page samplers). The per-served-page CPU figure is computed inside the flow (app CPU ÷ served pages) and asserted against the AC-73 budget; the M2 row is asserted as AC-75's zero-budget. Flow timing stays inside the NFR-06 per-flow budget (the scenarios are ≈ 25 s of scripted scrolling; the flow's fixture import is the multi tier, the same the other reader flows already import).

**Budget calibration (DR-202).** The first four runs of this flow measured 305.7 / 319.3 / 321.8 / 331.1 ms per served page against the drafted 300 ms budget — over budget, while the flow's request audit shows the pipeline working as designed (each of the 100 requested pages served exactly twice, zero re-requests, all served). A throwaway bench at the flow's exact widths put the pipeline itself at 229–237 ms/page (render 6–8, encode 217–222, IO remainder; every encoder variant equal or slower — the chosen encoder is the best available on the `image` dependency), locating the remaining ≈ 90 ms/page in the app's request plumbing (invoke dispatch + WebView2 asset streaming + queue handling) — the same gap the baseline M1 row carries (447 ms/page with the old encoder). AC-73's budget is re-calibrated to **≤ 350 ms/page** on this method (the 300 figure was calibrated from DR-196's pipeline-only bench model, which excluded the plumbing this flow measures); the flow records the pipeline/plumbing breakdown in its output rows. The bench was deleted after the decision (DR-202).

### 3.6 View modes (FR-17 MODIFIED / UI-34)

**State.** `viewMode: 'continuous' | 'single' | 'facing'` in the reader store — the single source for the layout, the strip control's active state, and the navigation semantics (the DR-156 one-state-source discipline). Default `continuous`. Changing mode keeps `currentPage` and re-lays out around it. Nothing in Rust changes: view mode is a frontend layout concern; the serving pipeline (`app_pdf_page`, the two-stage request order, the reader cache) serves one page per request regardless of mode.

**Continuous.** The released implementation unchanged: vertical stack, per-page geometry offsets, mount window, `overflow-anchor: none`; **pages carry `margin-inline: auto` (DR-205 — centered below fit width, margins collapse to zero above it so an over-wide page stays fully reachable; `align-items: center` rejected for the same reason).**

**Single.** Only the current page is mounted. **The container scrolls (amended at build by DR-204: `overflow: auto` — vertical always, horizontal when zoomed beyond the width); the page is centered when it fits and top-aligned when taller — flex centering with `margin: auto` on the page box, the standard scroll-container pattern (`justify-content: center` alone clips a taller child's top beyond reach, which is what left the fit-width page bottom unreachable in the shipped rule).** The current page becomes index-driven instead of scroll-driven — the same store value drives the layout; prev/next, the page field, `PgUp`/`PgDn` (page ±1) and `Home`/`End` (first/last) all go through the existing `goToPage` path, which in single mode changes the mounted index instead of scrolling. **Edge navigation (DR-204; the gesture rule replaced by DR-227): a wheel event whose direction points past a reached scroll edge advances exactly one page in that direction through the same `goToPage` path — no accumulation (the superseded rule — accumulated overscroll advancing one page per full page pitch — is quoted in DR-227); one wheel event never advances more than one page. The edge test is the container's own scroll position (within 2 px of either end), factored as a shared helper the wheel handler and the keyboard notch handler (UI-39) both call.** **Adjacent-page prefetch (DR-219, window extended by DR-224).** The mount effect keeps its released shape — request the current page first — and, once the current page's image has arrived at the current width (the same gate the continuous/facing branches already use), requests the current page ± 6 window through the same `requestPage` path: the same overscan value the continuous mount window uses (6, exported from `virtual.ts` as the single rule), clamped to the document bounds, queued movement-direction-first — the store records `lastNavDirection` (the sign of the last navigation's page delta; forward is the initial default), and the window's pages on the side the reader is moving come before the pages on the other side. no-op for pages already served at that width, never for out-of-document indices, bounded at thirteen requests per state. The served window lives only in the store's image cache — the mount stays one page, and the measured budgets are untouched (AC-73/AC-75 run in continuous; NFR-08's page-jump budget is helped, not stressed: a navigation to a prefetched page is served from cache). The user-visible effect: the next/prev controls, `PgUp`/`PgDn` and the edge navigation present the next page as an image swap, not as a fresh serve — the same no-blank guarantee continuous mode gives its scroll (the user's request of 2026-11-09; the literal "preload all pages" reading — the whole document — was discussed and rejected for its measured cost: ≈ 38 minutes of background encoding and a multi-GB cache at 10 000 pages, DR-224).

Fit-width measures the single page against the viewport width; the zoom modes are §3.16.

**Facing.** Rows of page pairs (a flex row with the standard 12 px gap, **each row carrying `margin-inline: auto` — centered below fit width, margins collapse to zero above it, DR-205**), the rows stacked vertically; row geometry derives from the two page heights (row offset step = max(page heights) + gap). Pages pair consecutively in reading order — (1,2), (3,4), … (OQ-43 closed → DR-180). The current page is the page whose row contains the viewport center; the page field shows that row's first page; entering a number opens the row containing it (`goToPage` on the row's first page); prev/next and `PgUp`/`PgDn` move one row. Fit-width derives each page's display width from `(container width − 12 px) / 2`; zoom steps multiply from there. An unpaired last page renders alone in its row — the layout degrades without a special case.

**Mode control.** Three icon-only buttons with tooltips after the zoom group in `ReaderControls` (the UI-13 icon-only pattern; new i18n keys `reader.view.single` / `reader.view.continuous` / `reader.view.facing`; three new glyphs in `icons.ts` — one page, a stack, a two-page spread). The active mode renders active, the released toggle pattern (UI-09).

**Keyboard navigation (UI-39/DR-228).** The `ReaderApp` key map gains the arrow keys. `ArrowLeft`/`ArrowRight` call the store's `stepPage(∓1)` — the strip buttons' own path (one page; one pair in facing). `ArrowUp`/`ArrowDown` call a store `scrollNotch(±NOTCH)` (NOTCH = 100 CSS px, one wheel notch): in continuous and facing it delegates to the view's existing `onScrollBy` callback; in single it delegates to a view-registered notch handler that applies the DR-227 edge rule through the shared edge helper — at a reached edge a page step through `goToPage` with the wheel's landing rule, otherwise `scrollBy(0, ±NOTCH)` on the container. Guards, in order: the released `isTextTarget` guard (the page field owns the keys while focused) runs first; the arrow keys additionally no-op while any overlay is open (`feedback.overlayCount > 0`) — the ToC panel's own `ArrowRight`/`ArrowLeft` entry handling (UI-33) and every menu/dialog keyboard behavior are untouched; the released keys' behavior is unchanged.

**Harness.** A new named flow `flowReaderViewModes` in the `reading-pdfs` area (own data directory per the AC-60 rule): the AC-79 and AC-80 rows against multi-192 (even page count — clean pairs) and a 1-page special fixture (the unpaired case). Modes are changed only by clicking the real control — the flow drives the shipped UI path, never internal state.

**What stays invariant:** serving, the page cache, the mount rule, the NFR-08/NFR-09 budgets (measured in the default continuous mode), covers, window chrome. A view mode changes which pages are visible at once, not what one page costs.

### 3.9 Size display by magnitude: bytes, kilobytes, megabytes (UI-36, rule revised by DR-208)

**Change (revised at build by DR-208).** `ui/src/lib/format.ts`: `formatBytes(n)` selects the unit by magnitude, every value through `Intl.NumberFormat` byte-unit formatting with `unitDisplay: "short"`: `n < 1_000` renders the `bytes` unit with no fraction digits (`512 B`); `1_000 ≤ n < 999_950` renders the `kilobyte` unit with `maximumFractionDigits: 1, minimumFractionDigits: 0` (`2 kB`, `12.5 kB`, `999.9 kB`); `n ≥ 999_950` renders the `megabyte` unit with 1 fraction digit below 100 000 000 and 0 from there (`1 MB`, `2.4 MB`, `125 MB`). The kB→MB boundary at 999 950 is the point where one fraction digit would render `1 000 kB` — the MB band takes over there so no value rounds into a four-digit kB. `n === 0` renders `0 B`. The two-fraction band and the `<0.01 MB` honest-floor literal are removed with their `format.sizeFloor` catalog key (R7.4 — its only consumer is gone). Call sites are unchanged (`DocumentRow.svelte` only, after UI-03 removes the card's use); the DTO, the sort whitelist and every byte value in the backend stay as they are — this is display formatting only.

**Why one decimal base across units:** the released formatter already rendered kB/MB on the 1000-base (that is `Intl`'s byte-unit convention), and the user's requests span both units — "MB" (DR-185) for the large-file case and "KB or Byte" (DR-208) for files under 1 MB. Binary MiB (the Windows Explorer base) was considered and rejected (DR-185): `Intl`'s `mebibyte` unit support is newer and unevenly localized, and one app must not mix bases between what it shows and what it sorts on. The revised rule keeps unit-per-magnitude rendering with the fixed fraction bands the MB request introduced for the megabyte range.

**Test contract.** `format.test.ts`'s size cases assert the §3.9 rule band by band, keeping the file's locale-agnostic-by-construction pattern: each band asserts against a reference `Intl` byte-unit formatter built with the same options (`512 → "512 B"`, `2_048 → "2 kB"`, `12_500 → "12.5 kB"`, `999_949 → "999.9 kB"`, `999_950 → "1 MB"`, `2_400_000 → "2.4 MB"`, `125_000_000 → "125 MB"`), plus the literal `0 → "0 B"` case; the floor-literal case is deleted with the mechanism. ### 3.10 Vertical content inset (UI-19 MODIFIED)

**Mechanism.** `DocumentList.svelte` and `DocumentGrid.svelte` carry the released horizontal inset as `padding-inline: var(--content-gutter)` on their `.window` container — the released rule is "the visual inset lives on the window containers" (v0.0.4 §3.8), and the vertical inset joins it: `padding-top: var(--content-gutter)` on both containers, **plus `padding-bottom: var(--content-gutter)` on the list window only (corrected at build by DR-200: measured, `padding-top` alone leaves the last row flush on the status bar — the fully translated window box extends the scrollable extent to exactly the content's bottom edge; symmetric padding makes the list's shift uniform. The shift is covered by the window function's existing ≥6-item overscan (≥ 6 rows / ≥ 6 blocks — far more than 12 px), so mid-scroll the viewport top stays continuously covered; the gap is visible where it is meaningful: at the top of the content, and — because the window's box extends 12 px past the spacer's bottom when the last block is mounted — at the end of the scroll, 12 px above the status bar hairline. `nearEnd`'s load-more threshold is measured against the offsets, so it fires 12 px of scroll earlier: harmless, unchanged.

**Value.** 12 px, the user's "consistency" asked for exactly the existing value. 8 px (the toolbar's internal control gap — a chrome-internal distance, not chrome-to-content), 16 px (a dialog-internal section gap) and 24 px (off the 4 px scale this app standardized in UI-27) were considered and rejected (DR-186). The toolbar and status bar hairlines stay exactly as released: the gap sits between the hairline and the content, it does not replace the separator.

**Test contract.** The content-gutter flow (AC-39's method) is extended, not replaced: at the top of the scroll the first row/card's top edge measures 12 px below the toolbar's bottom edge (the token's own value) in both views; at a mid-scroll position rows/cards render continuously with no gap band at the viewport top; at the end of the scroll the last row/card's bottom edge measures 12 px above the status bar's top edge; the released horizontal-gutter and width-matrix checks keep their numbers, and the mounted-node bound check with the 10 000-document fixture is unchanged. `SPEC-ALL-TESTS.md` gains the extended checks when the change lands.

### 3.16 Zoom model re-anchored: fit modes and actual size (UI-30 further MODIFIED, DR-221)

### 3.19 Cover appearance on generation completion (FR-16 further MODIFIED, DR-231)

**Cause (measured).** Two defects, one pipeline:

1. *The freeze.* The command wrappers (`commands.rs:66/77`) run the whole import inside `db.with(...)` — the library's single Mutex-guarded connection (`lib.rs:76-106`) — for the run's full duration, and `service.rs:285` performs `pdfmeta::extract` per file **inside** that lock. Synchronous commands (search, categories, settings reads — `library_search` is a sync `pub fn` running on the app's main thread) block on that mutex: while a chunk works, every window stops answering.
2. *The invisible progress.* `service.rs:24` defines `CHUNK: usize = 500` and emits one `library_job_progress` per chunk, only after the chunk's work. An import of ≤ 500 files emits exactly one event — the final one — and the frontend clears the bar at `processed >= total` (`feedback.svelte.ts:71-72`), so for any ordinary import the bar never appears.

**Design (pipeline re-anchor).** The service functions take `&Db` instead of `&Connection`, and the command wrappers drop the outer `db.with`:

1. **Plan** (one short read transaction): walk the paths / the folder, resolve each against the existing rows — duplicate skip, typed skips — producing the candidate list. No metadata extraction here.
2. **Open progress:** emit `library_job_progress` with `processed: 0`, `total: candidates.len()` before any per-file work, so the bar appears for an import of any size. A zero-candidate import emits nothing new; the completion-toast path is unchanged.
3. **Chunk loop** (`CHUNK: usize = 25`): for each candidate in the chunk, `pdfmeta::extract` runs with **no connection held**; then one short `db.with` write transaction inserts the chunk's rows and its category assignments (FR-10 auto-assign unchanged; one transaction per chunk honors R2's multi-table rule); commit; then emit the progress event with the new processed count. A search arriving while a chunk extracts acquires the mutex immediately; one arriving during the write transaction waits milliseconds, not for the whole import.
4. **Finish:** the existing completion path — final progress event, `status_updated`, completion toast — is unchanged.

The same loop serves `import_folder` and **Rescan** (FR-12): the rescan pipeline shares the chunk loop and the in-lock extraction, and re-anchoring both keeps one pipeline shape. The user's request names import; rescan shows the identical freeze and the identical invisible progress, and fixing only one of the two would leave the other to be re-reported — recorded as the agent's decision under DR-193.

**Progress semantics.** With the opening event and per-chunk events the bar shows from the first moment and advances every ≤ 25 files; the frontend's existing clear-at-completion rule stands and now fires only at the real end. The bar's rendering, the status bar layout and the completion toast are unchanged.

**Interaction budget.** "Responsive" is asserted behaviorally, not by a new timing contract: AC-101's real-app row types a search while an import is in flight and requires its results. The Rust half asserts the event audit (opening event, per-chunk events, chunk bound 25, final event) through the test `EventSink`, and the released 10 000-file timing assertions (NFR-02, `flowImport10k`) stay green with the chunked pipeline — the per-chunk transaction cost is bounded by the chunk bound and measured by those existing tests.

**What does not change.** Import semantics (auto-assign, duplicate skip, typed skips, folder walk), the `JobProgress` payload shape, the completion toast, cover enqueueing at import, and the DB schema.

**Test mapping:** AC-101.
