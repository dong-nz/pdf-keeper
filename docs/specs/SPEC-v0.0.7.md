## 0. Scope and version

**Version set by the user 2026-11-07 (DR-173): v0.0.7** — the user opened this draft with "include performance in the new spec v0.0.7", on top of the reader-control placement direction agreed in the same discussion (DR-172), and brought the reader table of contents into scope (OQ-41 closed → DR-177). On the 0.0.x line (DR-91) this is a feature release: it adds a user-facing capability (`FR-18`), modifies a released UI requirement, and adds a measured performance requirement. v0.1.0 stays reserved for the app-updates release (`FR-19`+, DR-47/DR-48 as re-reserved by OQ-36/DR-139 and again by DR-177).

**ID policy (updated 2026-11-08 by DR-182–DR-190):** consumes `FR-18` for the reader table of contents; app-updates re-reserved at `FR-19`+ (the reservation moves a third time, by user decision). One new `NFR-09`. Defects from `D19`. ACs from `AC-73`. OQs from `OQ-43` (`OQ-45` opened by DR-188, closed by DR-189). **What this release is** (the user's scope decisions of 2026-11-07, DR-172/DR-173/DR-177/DR-178/DR-179):

- **D19 — page-encoding cost** (Rust core): the measured cost of serving a reader page is dominated by PNG encoding (§3.1 M3); it is reduced by tuning the PNG encoder on the existing `image` dependency (OQ-42 closed → DR-178).
- **FR-18 (new) — reader table of contents**: the built-in reader shows a PDF's outline when it has one (OQ-41 closed → DR-177; design §3.5).
- **NFR-09 (new)** — reader scrolling and page serving get measured budgets (the harness rows of §4), locking the verified baselines in as regression guards and bounding the page-serving CPU cost.
- **UI-30 (MODIFIED)** — the reader control strip moves to the window's bottom edge; the window chrome stays at the top (the placement direction the user chose 2026-11-07, DR-172).
- **UI-33 (new)** — the ToC control in the strip and its panel.
- **FR-17 (MODIFIED) + UI-34 (new)** — view modes in the reader control bar: single page / continuous / facing (the user's request of 2026-11-07, DR-179; design §3.6; consecutive pairing and session-only scope decided by the user — OQ-43/OQ-44 closed → DR-180/DR-181).
- **UI-35 (new)** — the light ramp re-authored to the official Dracula **Alucard** palette (the user's request of 2026-11-08, DR-182; the light variant v0.0.6 §0 named as a candidate; design §3.7).
- **UI-03 (MODIFIED)** — grid cards no longer render the document size and date-added line (the user's request of 2026-11-08, DR-183), and their hover action icons render on an opaque ground instead of transparently over card text (the user's request of 2026-11-08, DR-184); card facet design §3.8. Extended by DR-188 (the user's request of 2026-11-08): the list row's cover is enlarged to 51×72 and inset 8 px from the row's separator lines, the row base height 64→88 px (OQ-45 closed as option B → DR-189); design §3.12.
- **UI-36 (new)** - document size is displayed in megabytes wherever the app shows it (the user's request of 2026-11-08, DR-185; design §3.9).
- **UI-19 (MODIFIED)** - the released 12 px content gutter extends vertically: rows and cards keep a 12 px gap to the toolbar's bottom edge instead of starting flush against its hairline (the user's request of 2026-11-08, DR-186; design §3.10).
- **UI-37 (new)** - every tooltip the app shows is rendered by the app's own themed tooltip, on the active ramp's floating-chrome ground; the OS-drawn native-title tooltips that remain today are replaced (the user's request of 2026-11-08, DR-187; design §3.11).
- **UI-17 (MODIFIED)** - the Settings menu's theme submenu becomes one action item that cycles Light -> Dark -> Auto (= follow-the-system); the mode is named Auto and gets a half light / half dark icon (the user's request of 2026-11-08, DR-190; design §3.13). The same item carries the settings dialog's restructure: its Library section is removed - the dialog holds the configuration controls and a Data location section (the user's request of 2026-11-08, DR-191; design §3.14).
- **UI-21 (MODIFIED)** - the data-location row moves into that Data location section and gains one action: an icon that opens the configured path in the OS file manager, through one new whitelisted command; its read-only rules stand (DR-191; design §3.14).

**Out of scope, and why — the corrected baseline (DR-174/DR-175) removed two candidates that the pre-draft discussion had assumed:**

- **Document handle cache — out.** Measured: opening a document through pdfium costs 0.2–2.0 ms and a second page on an open document saves nothing measurable (M3). A cache would add invalidation surface for ≈ 1 ms per page. The service keeps opening each document per request.
- **Scroll-geometry memoization / scroll-event throttling — out.** Measured: a warm back-and-forth scroll costs the same at 192 and 1 000 pages (ScriptDuration 0.043 s vs 0.044 s over 9.6 s), with zero dropped frames and zero long tasks (M2). The per-event geometry recomputation the code does is not a measurable cost; RULES ("do not rewrite working code without a clear reason") says leave it.
- Carried unchanged from v0.0.6 §0: persistent page cache, in-memory page delivery (R5.4), PDF.js, prefetch/overscan changes, reading progress, text search/selection, and the parked candidates C3–C8. The reader ToC is **in** this release (OQ-41 closed → DR-177): `FR-18`, `UI-33`, design §3.5. The Dracula **Alucard** light variant is no longer parked — it is adopted by this release (`UI-35`, design §3.7, DR-182).

## 2. Requirements

### Added

**FR-18 (Reader table of contents)** — text: *The built-in reader shows a document's table of contents when the PDF carries one: the reader's control strip offers a table-of-contents control that opens the document outline as a hierarchical list — entry titles with their target page numbers, nested entries indented by outline depth. Activating an entry jumps the page stack to that page. A document without an outline offers no table-of-contents control.* Scope: view and jump — no current-section highlight, no persisted collapse state, no outline editing. Note: consumes the `FR-18` slot; app-updates re-reserved at `FR-19`+ (DR-177).

**NFR-09 (Reader interaction budgets)** — text: *Reader scrolling and page serving are budgeted on measured cost, asserted by the verification harness's measured rows (AC-73/AC-75), not by a stopwatch. During the scripted cold forward scroll on the multi fixture tier, the app process spends at most the stated per-served-page CPU budget (AC-73), and every page the mount window requested is served by the end of the run. A scripted warm (cached) back-and-forth scroll on the 1 000-page fixture produces no served pages, no app-process CPU, no dropped frames and no main-thread long tasks (AC-75) — the state the corrected baseline measured (M2) and this release must not regress. The NFR-08 open / page-jump / zoom display budgets are unchanged by this release.*

**UI-33 (Table-of-contents control and panel)** — text: *When the opened document has an outline, the reader control strip carries a table-of-contents control (icon-only with tooltip, the released UI-13 pattern) at the end of the control group. Activating it opens a panel above the strip, anchored to the control with the released edge-flip behavior, listing the outline: entry titles with right-aligned target page numbers, nesting indented by outline depth; the panel scrolls with the standard scrollbar and is bounded like the released menus (UI-20/D5). Activating an entry jumps the page stack to its page through the same path as the page field and closes the panel. While the panel is open, `Esc` closes the panel and the window stays open; with no overlay open, `Esc` closes the window unchanged (UI-30). Activating the control again re-opens the panel. The control is not rendered for documents without an outline.*

**UI-34 (View modes)** — text: *The reader control strip carries a view-mode control after the zoom group: three icon-only buttons with tooltips — **single page**, **continuous**, **facing** — with the active mode rendered active. **Continuous** is the default and is the released behavior: pages form a continuous vertical scrollable stack. **Single page** shows exactly one page at a time, centered in the viewport area; scrolling is disabled and the document moves only through the navigation controls: prev/next, the page field, `PgUp`/`PgDn` (previous/next page) and `Home`/`End` (first/last page). **Facing** lays pages out side by side in **consecutive pairs in reading order (1|2, 3|4, … — OQ-43 closed → DR-180)**; pairs stack vertically with the same 12 px gap and scroll like the continuous stack; prev/next and `PgUp`/`PgDn` move one pair at a time; the page field shows the first page of the pair containing the viewport center, and entering a number opens the pair containing that page; a last page with no partner renders alone. Fit-width fits the visible unit to the viewport (in facing, each page at most half the viewport width minus the gap); zoom steps apply to each page. Changing mode keeps the current page visible and re-lays out around it. **View modes are session-scoped (OQ-44 closed → DR-181): a mode choice applies to the open reader window; every new reader window opens in continuous.** Page serving, the mount rule (UI-04), the page cache and the measured budgets are mode-independent: every visible page is served through the released pipeline.*

**UI-35 (Dracula Alucard light ramp)** — text: *The light ramp in `design-tokens.css` (`:root`) is re-authored to the official Dracula **Alucard** palette — the Dracula team's light variant (`dracula/cursor`, `dev/src/alucard.yml`, authors Lucas de França & Zeno Rocha, maintainers at draculatheme.com; the variant named as a candidate by `SPEC-v0.0.6.md` §0) — per the §3.7 mapping: surfaces, borders, text roles, accent and semantic colors with their hover variants, selection and hover grounds, scrollbar thumb. The dark ramp, the theme control and the `theme` setting key (UI-17) are unchanged; `system` resolution is unchanged (DR-101); `color-scheme: light` stays. The shipped contrast discipline applies unchanged to the re-authored ramp: every text-role use clears 4.5:1 on the exact ground it renders on (D11/DR-120), and text on a 12 % tint of its own color takes the hover value; where a source Alucard value does not clear the bar on a ground it is used on, the §3.7 mapping states the darkened substitution with its measured ratio — the same substitution rule that governed the dark ramp (DR-145/DR-146). Components change nothing: every surface reads these tokens (R4.5).*

**UI-36 (Document size display in megabytes)** — text: *Wherever the app displays a document's size, it displays it in **megabytes**: the value is `size / 1 000 000` (decimal MB — the same base the released byte formatter used when it rendered kB/MB), rendered through `Intl.NumberFormat` with the `megabyte` unit and short unit label (R8.1 stands: every user-facing format stays an Intl call; only the unit is fixed). The fraction rule is fixed by magnitude: two fraction digits below 1 MB, one below 100 MB, none from 100 MB up; a non-empty file that would round to `0.00` renders `<0.01 MB`; a zero-byte value renders `0 MB`. No other unit is ever rendered for a document size. After UI-03's card change, the app's only size display is the list row's size column; the rule governs it and any future display.* Design §3.9; AC-85.

**UI-37 (Tooltip surfaces and full coverage)** — text: *Every tooltip the app shows is rendered by the app's own tooltip wrapper over the kit primitive (the released §3.6 mechanism), and no tooltip is left to the OS-drawn native title. The wrapper's surface is the active ramp's floating-chrome ground — `--surface-1` with the app's 1 px hairline border and `--shadow-overlay` — the same overlay language the menus and modals already use, so a tooltip's text always reads against a distinct ground, whatever it lands on (toolbar, hovered row or card, menu, dialog, reader chrome), and it follows the theme the window is actually showing (UI-17's resolved ramp; reader windows included). The text a tooltip carries is unchanged everywhere it exists today: the control labels (UI-13, D4 unchanged), the full text of every ellipsized title/author/notes line in rows and cards (AC-08's claim, new mechanism), the stored path on the missing flag and badge (AC-47's claim, new mechanism), the reader window's document name, the category row's action names, the delete dialog's file note, the column steppers in the View menu and Settings. Where the app's tooltip replaces a native `title`, the attribute is removed, not kept beside it. Tooltips on controls open on pointer hover and keyboard focus as released; tooltips on text surfaces open on pointer hover — the trigger behavior the native title had, stated honestly rather than promised beyond it. The released design ruling "a tooltip is chrome, not an overlay … carries no shadow" (v0.0.3 §3.6) is corrected: a tooltip is a small floating overlay and carries the ramp's overlay ground and shadow.* Design §3.11; AC-87.

## 3. Technical design

Stages: **Rust core** (`src-tauri/src/pdf/` — the `serve_page` encode stage; `src-tauri/src/pdfmeta/` — outline reading; one new Tauri command, `app_pdf_outline`, a thin wrapper per R1.2) → **Tauri commands** (whitelist + the typed frontend client mirror it; the existing command-set equality test catches any drift) → **UI** (`ui/src/ReaderApp.svelte` layout and `ReaderControls` placement; the ToC control and panel; the view-mode control and the mode-aware layout in `ReaderView`) → **fixtures + harness** (`scripts/make-fixtures.mjs` outline extension; new measured, ToC and view-mode flows). No data-model change, no new crate: the encoder knobs are on the already-pinned `image` 0.25.10 (verified present in the vendored source), and outline reading uses the already-pinned `lopdf` 0.47.

### 3.1 Baseline measurements (the factual base of this spec)

Measured 2026-11-07 on the reference machine against the debug app binary (`src-tauri/target/debug/pdfkeeper.exe` — the same binary the harness runs), with two throwaway tools since deleted (DR-174): `scripts/probe-reader-cpu.mjs` (CDP metrics read at `result.metrics`, process CPU via `Get-Process` over the full process tree including the app process, served pages counted from the reader cache directory) and `src-tauri/tests/bench-encode-tmp.rs` (Rust, pdfium + `image` 0.25.10).

**M1 — scripted cold forward scroll** (100 wheel steps × 400 px @ 120 ms inside the page stack, from the top):

| Fixture | Served pages | app-process CPU | renderer main thread | dropped frames |
|---|---|---|---|---|
| multi-1000 | 32 | **14.52 s** (≈ 453 ms/page) | ScriptDuration 0.071 s, Layout 0.018 s, TaskDuration 0.228 s | 0 / 913 |
| multi-192 | 32 | **14.30 s** (≈ 447 ms/page) | ScriptDuration 0.052 s, Layout 0.019 s, TaskDuration 0.212 s | 0 / 915 |

The app-process cost per page is the same for a 192-page and a 1 000-page document → the cost is per served page, not per document size. The renderer stays responsive throughout: no dropped frames, no long tasks. The user-visible cost is page *availability* (how long a page takes to arrive and to reach full sharpness), not scroll jank.

**M2 — scripted warm back-and-forth scroll** (80 steps × 400 px @ 120 ms over the already-visited range; pages re-enter the mount window from the reader cache):

| Fixture | Served pages | app-process CPU | renderer main thread | dropped frames | long tasks |
|---|---|---|---|---|---|
| multi-1000 | 0 | 0.031 s | ScriptDuration 0.044 s | 0 / 758 | 0 |
| multi-192 | 0 | 0.047 s | ScriptDuration 0.043 s | 0 / 760 | 0 |

Warm scroll is flat in document size and already clean. The WebView2 processes spend 0.7–0.9 s re-decoding cached page images as they re-enter the mount window — the browser's own decode, not app work.

**M3 — per-page cost split** (bench, multi-192 page 1, debug build):

| Stage | @ 966 px | @ 1932 px |
|---|---|---|
| `load_pdf_from_file` (document open) | 2.0 ms | 0.2 ms |
| pdfium raster | 6.2 ms | 4.8 ms |
| PNG encode, current default (`DynamicImage::save`) | **82 ms** (33 KB) | **332 ms** (109 KB) |
| PNG encode, `PngEncoder::new_with_quality(Fast, Sub)` | 52 ms (37 KB) | 207 ms (117 KB) |
| PNG encode, `Uncompressed` + `NoFilter` | 20 ms (4 718 KB) | 80 ms (18 871 KB) |

Summed across the two-stage pattern a page is served at (preview ≈ 966 px + full ≈ 1932 px): ≈ 427 ms — matching M1's measured ≈ 450 ms/page. **Encoding is ≈ 90 % of the per-page app CPU; opening and rastering a document are noise.** The encoder knobs are present in the pinned `image` 0.25.10 (`image::codecs::png::PngEncoder::new_with_quality`, `CompressionType`, `FilterType` — verified against the vendored source).

**M4 — correction of the pre-draft numbers (DR-174).** The numbers quoted in the 2026-11-06/07 discussions (warm-scroll ScriptDuration 1.31 s scaling ~6× with document size; cold-scroll jank 61 dropped frames; per-page cost attributed to document re-opening and O(N) geometry recomputation) came from a probe run with two instrumentation defects: the CDP metrics response was read at the wrong path (the list is nested under `result.metrics` — every metric diff came out zero or stale) and the process tree omitted the app process itself. The corrected re-run above supersedes them. The claims they supported — that warm scroll recomputes geometry expensively, and that re-opening documents is a real cost — did not reproduce: they leave the scope (§0).

### 3.2 Encoding change (D19, `src-tauri/src/pdf/`)

`serve_page` currently renders through the RenderService and then encodes with `image::DynamicImage::save` (the PNG encoder's default balanced compression + adaptive filter). The change replaces that single call with `PngEncoder::new_with_quality(writer, <compression>, <filter>)` — option B, chosen by the user (OQ-42 closed → DR-178). The exact compression/filter values are fixed at build time from measured rows (the bench's `Fast` + `Sub` row — 332 ms → 207 ms at 1 932 px, −38 % — is the expected landing point; the build may measure a better row and take it, recording the choice in the Decision Log); AC-73's measured row proves the result. The cache contract is untouched: same `<reader_dir>/<doc-key>/<page>-<width>.png` key, same PNG format, same two-stage preview/full serving, same interactive-first queue. **Covers stay on the current encoder**: their cache is persistent (bigger files are a real disk cost), the cover pipeline already meets its measured budgets (v0.0.5), and this release does not touch it (AC-74 asserts it stays green). Option C (JPEG pages) was considered and not chosen (DR-178): it would have traded lossy artifacts in a reading app for speed this release does not need; if it is ever revisited it needs its own Decision Log entry before code (R3.4).

The other multi documents, `multi-1000` included, keep no outline — UI-33's negative case. The regenerated multi-192 differs from the released file only in outline structure: page content streams, page count, and geometry are identical, so the released page-identity assertions (AC-61/AC-65) are unaffected; its cover re-keys with the changed file hash and regenerates automatically (hash-keyed cache, DR-113).

**Rust.** `pdfmeta` — the module that already owns `lopdf` — gains `outline(path) -> Result<Vec<OutlineEntry>, AppError>` with `OutlineEntry { title, page, depth }`: load the document, take the catalog's `/Outlines`, walk item dictionaries through lopdf's outline helpers (`get_outline` / `get_outlines` with named-destination resolution), resolve each entry's `/Dest` (or `/A` → `/D`) to a 1-based page number with `get_destination_page_number`, and take depth from the First/Next nesting. Titles decode through lopdf's string decoding (PDFDocEncoding / UTF-16BE). ### 3.6 View modes (FR-17 MODIFIED / UI-34)

**State.** `viewMode: 'continuous' | 'single' | 'facing'` in the reader store — the single source for the layout, the strip control's active state, and the navigation semantics (the DR-156 one-state-source discipline). Default `continuous`. Changing mode keeps `currentPage` and re-lays out around it. Nothing in Rust changes: view mode is a frontend layout concern; the serving pipeline (`app_pdf_page`, the two-stage request order, the reader cache) serves one page per request regardless of mode.

**Continuous.** The released implementation unchanged: vertical stack, per-page geometry offsets, mount window, `overflow-anchor: none`.

**Single.** Only the current page is mounted, centered in the viewport area (the container is `overflow: hidden`; wheel scroll does not move the document). The current page becomes index-driven instead of scroll-driven — the same store value drives the layout; prev/next, the page field, `PgUp`/`PgDn` (page ±1) and `Home`/`End` (first/last) all go through the existing `goToPage` path, which in single mode changes the mounted index instead of scrolling. Fit-width measures the single page against the viewport width; zoom steps multiply from there.

**Facing.** Rows of page pairs (a flex row with the standard 12 px gap), the rows stacked vertically; row geometry derives from the two page heights (row offset step = max(page heights) + gap). Pages pair consecutively in reading order — (1,2), (3,4), … (OQ-43 closed → DR-180). The current page is the page whose row contains the viewport center; the page field shows that row's first page; entering a number opens the row containing it (`goToPage` on the row's first page); prev/next and `PgUp`/`PgDn` move one row. Fit-width derives each page's display width from `(container width − 12 px) / 2`; zoom steps multiply from there. An unpaired last page renders alone in its row — the layout degrades without a special case.

**Mode control.** Three icon-only buttons with tooltips after the zoom group in `ReaderControls` (the UI-13 icon-only pattern; new i18n keys `reader.view.single` / `reader.view.continuous` / `reader.view.facing`; three new glyphs in `icons.ts` — one page, a stack, a two-page spread). The active mode renders active, the released toggle pattern (UI-09).

**Harness.** A new named flow `flowReaderViewModes` in the `reading-pdfs` area (own data directory per the AC-60 rule): the AC-79 and AC-80 rows against multi-192 (even page count — clean pairs) and a 1-page special fixture (the unpaired case). Modes are changed only by clicking the real control — the flow drives the shipped UI path, never internal state.

**What stays invariant:** serving, the page cache, the mount rule, the NFR-08/NFR-09 budgets (measured in the default continuous mode), covers, window chrome. A view mode changes which pages are visible at once, not what one page costs.

### 3.9 Size display in megabytes (UI-36)

**Change.** `ui/src/lib/format.ts`: `formatBytes(n)` becomes `megabytes.format(n / 1_000_000)` where `megabytes = new Intl.NumberFormat(undefined, { style: "unit", unit: "megabyte", unitDisplay: "short", minimumFractionDigits, maximumFractionDigits })` built per magnitude band (2 fraction digits below 1 MB; 1 below 100 MB; 0 from 100 MB up). The two guards: `n === 0` renders `0 MB`; `0 < n < 5_000` renders the honest floor `<0.01 MB` (a literal through the existing i18n layer — one new catalog key, the `<…` prefix is a string, not a format). Call sites are unchanged (`DocumentRow.svelte` only, after UI-03 removes the card's use); the DTO, the sort whitelist and every byte value in the backend stay as they are — this is display formatting only.

**Why decimal MB:** the released formatter already rendered kB/MB on the 1000-base (that is `Intl`'s byte-unit convention), and the user's request says MB. Binary MiB (the Windows Explorer base) was considered and rejected: `Intl`'s `mebibyte` unit support is newer and unevenly localized, and one app must not mix bases between what it shows and what it sorts on. Mixed units (kB below 1 MB, MB above — the released behavior) is what the request asks to replace.

**Test contract.** `format.test.ts`'s "formats sizes as short byte units" case is replaced by the MB rule, keeping the file's locale-agnostic-by-construction pattern: each band asserts against a reference `Intl` megabyte formatter built with the same options, plus literal assertions for the `<0.01 MB` floor and the `0 MB` case. The row meta-column flow (AC-39's method) gains the size-cell text check: the rendered cell equals `formatBytes(doc.size)` for fixture documents whose byte sizes the manifest records. The fixed meta-column geometry (UI-20) is unchanged; its measurements are re-verified at build. `SPEC-ALL-TESTS.md` is updated with the replaced and added cases when the change lands.

### 3.10 Vertical content inset (UI-19 MODIFIED)

**Mechanism.** `DocumentList.svelte` and `DocumentGrid.svelte` carry the released horizontal inset as `padding-inline: var(--content-gutter)` on their `.window` container — the released rule is "the visual inset lives on the window containers" (v0.0.4 §3.8), and the vertical inset joins it: `padding-top: var(--content-gutter)` on the same containers (`SkeletonRows.svelte` mirrors it the way it already mirrors the side gutter — its placeholder rows then land where real rows land, UI-28). No new token: `--content-gutter` is the app's existing chrome-to-content distance (the side gutters, the toolbar's and status bar's own `padding: 0 12px`, `--menu-edge`, the card gap), and R4.5 forbids minting a second near-duplicate value.

**Why the window containers and not the scroller or the area.** A persistent band (padding/margin on the scroller or on `.document-area`) would shrink the windowing viewport permanently — `viewportHeight` is read from `scroller.clientHeight` — and would push the bulk bar 12 px off the toolbar chrome it pairs with. The window padding is a uniform visual shift of all mounted content: every row/card sits at its computed offset + 12 px, so `offsets`, `totalHeight`, `padTop`, the width math (`clientWidth − 2 × CONTENT_GUTTER` — vertical padding does not change `clientWidth`) and the mounted-node bound (NFR-01) are untouched. The shift is covered by the window function's existing ≥6-item overscan (≥ 6 rows / ≥ 6 blocks — far more than 12 px), so mid-scroll the viewport top stays continuously covered; the gap is visible where it is meaningful: at the top of the content, and — because the window's box extends 12 px past the spacer's bottom when the last block is mounted — at the end of the scroll, 12 px above the status bar hairline. `nearEnd`'s load-more threshold is measured against the offsets, so it fires 12 px of scroll earlier: harmless, unchanged.

**Value.** 12 px, the user's "consistency" asked for exactly the existing value. 8 px (the toolbar's internal control gap — a chrome-internal distance, not chrome-to-content), 16 px (a dialog-internal section gap) and 24 px (off the 4 px scale this app standardized in UI-27) were considered and rejected (DR-186). The toolbar and status bar hairlines stay exactly as released: the gap sits between the hairline and the content, it does not replace the separator.

**Test contract.** The content-gutter flow (AC-39's method) is extended, not replaced: at the top of the scroll the first row/card's top edge measures 12 px below the toolbar's bottom edge (the token's own value) in both views; at a mid-scroll position rows/cards render continuously with no gap band at the viewport top; at the end of the scroll the last row/card's bottom edge measures 12 px above the status bar's top edge; the released horizontal-gutter and width-matrix checks keep their numbers, and the mounted-node bound check with the 10 000-document fixture is unchanged. `SPEC-ALL-TESTS.md` gains the extended checks when the change lands.

### 3.12 List-row cover enlargement and the row gap (UI-03 MODIFIED, row facet)

**What today is (measured).** The list cover is exactly the row: `ROW_HEIGHT = 64` (`ui/src/lib/virtual.ts`, mirroring the `--row-height` token) and `ROW_COVER_WIDTH = round(ROW_HEIGHT × 210/297) = 45`, derived from it; `DocumentRow.svelte` renders the `Cover` at 45×64. Each row carries `border-bottom: 1px solid var(--border-hairline)` — the row's bottom line — and the row above's border is its top line, so the cover is flush against both horizontal lines of its row. The row's own horizontal rhythm is `gap: 8px` between cover and text. A cover larger than 45×64 is only possible with a taller row: the cover keeps the A4 ratio, so its size is derived from the row's height. That is why the row base height was the decision (OQ-45, closed → DR-189).

**Mechanism.** The cover stays derived from the row — one source, never two numbers. A new constant `ROW_COVER_GAP` mirrors a new `--row-cover-gap` token (the lockstep rule `ROW_HEIGHT`/`CONTENT_GUTTER` follow, R4.5):

- `coverHeight = ROW_HEIGHT − 2 × ROW_COVER_GAP`
- `ROW_COVER_WIDTH = round(coverHeight × 210 / 297)` — the A4 ratio holds by construction.

`DocumentRow` passes the derived box to the existing `Cover` component; the row keeps `align-items: center`, so the cover is vertically centered and the gap appears above and below it against the row box's edges and the separator hairlines — no per-row margins, no new layout CSS beyond the sizes. `rowHeight(doc) = ROW_HEIGHT + lines × 18` keeps the released 18 px metadata-line step (UI-03/AC-24): a row with author and notes grows by exactly the base delta. Every consumer that reads the token/constant follows the chosen numbers automatically — the windowing path (`rowOffsets`, the viewport bound), the skeleton placeholders (UI-28), the row-design flow. Released assertions that hard-code 64/45 (the `virtual.test.ts` row-block cases, the smoke harness's expected-row-height fixtures) are re-derived to the chosen numbers at build time — the same re-derivation the DR-99 metric change went through.

**Cover pipeline untouched.** The generated asset is 640×905 (`RENDER_TARGET_WIDTH`, FR-16/DR-113); the enlarged box (≤ 51×72 CSS px, ≤ 102×144 at 2× device scaling) is still served from the same asset. `RENDER_TARGET_WIDTH` does not change — no cache re-keying, no regeneration, no backend change of any kind.

**What does not change.** The row's content and order (UI-03's text), the 18 px line step, the hover actions line and its AC-33/AC-35 geometry, the meta column widths (AC-39), the grid card and §3.8's changes, the UI-19 insets including the new vertical one, favorite/selection states.

**The fork (OQ-45) and the decision.** The row base height trades rows-per-screen against cover legibility — the user's call. The options recorded in OQ-45, all on the 4 px scale (UI-27), all giving a cover larger than today's 45×64 (2 880 px²; percentages against that baseline):

| Option | Row base | Gap | Cover | Cover area | Rows per screen | Cover share of row |
|---|---|---|---|---|---|---|
| A | 80 px | 4 px | 51×72 | +27 % | −20 % | 90 % |
| **B — adopted (DR-189)** | 88 px | 8 px | 51×72 | +27 % | −27 % | 82 % |
| C | 84 px | 8 px | 48×68 | +13 % | −24 % | 81 % |

**OQ-45 closed 2026-11-08 → DR-189: the user chose B.** A (the same cover, but a 4 px gap that reads as an accident of rounding, not the requested breathing room) and C (a +13 % cover — half the request) rejected with the choice; B's density cost (rows per screen −27 %) is accepted by the request for a clearly bigger cover with a clearly visible gap — the 8 px equals the row's own internal 8 px rhythm.

**The numbers as fixed.** `--row-height: 88px` token and `ROW_HEIGHT = 88`; new `--row-cover-gap: 8px` token and mirrored `ROW_COVER_GAP = 8` constant; `coverHeight = 88 − 2×8 = 72`; `ROW_COVER_WIDTH = round(72×210/297) = 51`; a row with author and notes renders `88 + 2×18 = 124` px. `DocumentRow.svelte` passes the derived box to the existing `Cover` component; the row keeps `align-items: center`, so the 8 px gap appears above and below the cover against the row box's edges and the separator hairlines — no per-row margins, no new layout CSS beyond the sizes. Every consumer of the token/constant follows automatically — `rowOffsets` and the viewport bound, the skeleton placeholders (UI-28), the row-design flow — and the released assertions that hard-code 64/45 (`virtual.test.ts` row-block cases, the smoke harness's expected-row-height fixtures) are re-derived to 88/51×72/124 at build time, the DR-99 precedent.
