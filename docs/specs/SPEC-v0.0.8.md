**What this release is** (the user's brainstorm of 2026-11-10, ten items, DR-250):

- **FR-19 (new) — the Reading collection**: a per-document membership collection for documents the user reads, with a *Reading* view beside the existing special views and a row/card toggle; membership changes only through the user's action (design §3.2; OQ-47 closed as A — flag + special view, OQ-48 closed as B — manual only).
- **FR-20 (new) — password-protected PDFs**: the built-in reader opens protected documents through a password prompt; a confirmed password is remembered per document only when the user opts in (design §3.3; OQ-49 closed as C).
- **FR-21 (new) — rename a document's file from inside the application**: the file is renamed on disk, the record follows, the document's identity survives (design §3.4).
- **UI-40 (new) — *Open containing folder***: context-menu and Details action opening the file's folder in the system file manager (design §3.5).
- **UI-41 (new) — the bulk-bar favorite toggle**: one control replacing the current two items, its action chosen from the selection state (design §3.6).
- **UI-42 (new) — tag terminology**: the application calls its document groups **tags** in every user-facing surface **and in its internal names** (design §3.7; OQ-50 closed as B — the full rename).
- **UI-43 (new) — the Reading control set**: the Browse-menu *Reading* view item and the row/card/context-menu toggle (design §3.2).
- **UI-44 (new) — the import labels**: *Import files* → **Import PDFs** (design §3.8).
- **UI-29 (MODIFIED)** — the empty library state offers both import actions as equal outline buttons, *Import PDFs* (`Ctrl+I`) and *Import folder* (`Ctrl+O`), each keycap combination rendered below its button; `Ctrl+O` becomes a library-window shortcut (old text quoted in §2; design §3.9; the button composition is the user's Phase-B decision of 2026-11-10, DR-272, refined by DR-274, the shortcut combination set by DR-275).
- **D20 — the browser's default context menu on app chrome** (toolbar, status bar, bulk bar, reader chrome): suppressed application-side **everywhere, including text fields** (design §3.10; OQ-51 closed as B); the app's own menus are unchanged.
- **D21–D24 — the known-issue repairs** (roadmap §4, post-Ship pass of 2026-11-10): the 10k runner's stale toast label; the intermittent cold-run cover-queue drain test; the bottom-edge zoom clamping at the last page; measurement of the rare first-open outlier (design §3.11).
- **Workflow formalization (DR-252)** — the user's brainstorm Rules item: the Phase A / Phase B / Phase C verification sequence becomes the standing workflow of AGENTS stage 4, Phase C (the full suite) running **after every Ship** per the user's decision of 2026-11-10 closing the DR-192 experiment. `AGENTS.md` stage 4 is rewritten in this draft (Rule 8 record).

**Out of scope, and why:**

- **EPUB support — out of this release; roadmap candidate with recorded options.** The brainstorm names EPUB as direction ("same features as PDFs"). No EPUB code exists today; the technical options and their trade-offs are recorded in `docs/ROADMAP.md` §5 (DR-253). EPUB is a capability area of its own and needs its own release spec; it is not squeezed into this one.
- **App updates (`FR-22`+ after OQ-46) — unchanged reserved scope** (DR-47/DR-48 as re-reserved by DR-139/DR-177).
- **Cross-platform packaging + CI** (roadmap line 2), **full-text search**, **reading-position memory**, **reader tabs** — carried unchanged from the v0.0.7 §0 out-of-scope list and the roadmap §5.
- **Reading progress / last position**: FR-19 is a *collection* (membership), not a progress tracker; position memory stays a roadmap candidate.

### 3.2 The Reading collection (FR-19 / UI-43)

Model (OQ-47 closed as A, OQ-48 closed as B — DR-257):

- **Migration** (§3.7, DR-273): fresh databases get the `reading` column in the clean baseline (the same baseline carries the FR-20 column, §3.3); a version-1 database gets `ALTER TABLE documents ADD COLUMN reading INTEGER NOT NULL DEFAULT 0;` in its rebuild upgrade. No new table.
- **Service** (`service.rs`): `set_reading(conn, id, on)` (single and batch); `list_documents` gains the `reading_only` predicate beside the existing `favorites_only` / `missing_only` arms; `DocumentDto` gains `reading: bool`.
- **Command**: `library_set_reading(ids, on)` — thin wrapper (R1.2), added to the R1.3 whitelist and the typed client.
- **Manual only**: the `reading` flag is written **only** by `set_reading`. `app_open_reader_window` performs no membership write — opening a document does not mark it (the requirement's explicit rule).
- **UI**: `library.filter.reading_only` flag; `BrowseMenu.MODES` gains the fourth entry `{ mode: "reading", icon: "bookmark" }` with the live count; `RowActions` / `DocumentCard` / `ContextMenu` gain the toggle following the `actions.ts` favorite-toggle pattern (state-following icon/label); `icons.ts` gains the `bookmark` glyph path (24×24 grid, 2 px stroke — the released icon rules).
- The *Reading* view composes with search like the other modes; it is exclusive of the other filter modes (the released filter-mode rule unchanged).

### 3.3 Password-protected documents (FR-20)

- **Typed error**: new `AppError` variant `PasswordRequired { path }` → error payload kind `password-required` (R3.2; the payload stays a string the frontend maps to the prompt, not a raw error).
- **Rust core** (`pdf.rs`, `reader` render path): the load attempt passes the stored password when the row has one, otherwise `None`; a pdfium `InvalidPassword` failure maps to `PasswordRequired` instead of the generic render error. The same plumbing applies to cover rendering (`covers` queue passes the stored password when present; without one, the existing glyph fallback stays).
- **Storage** (OQ-49 closed as C — opt-in): the `pdf_password TEXT NOT NULL DEFAULT ''` column is part of the clean baseline (§3.7); a version-1 database gets it as `ALTER TABLE documents ADD COLUMN` in its rebuild upgrade — written **only when the user checks "Remember this password"** at a successful unlock. Plaintext in the user's own library database — the same trust model as notes today (local, single user, the data directory is the user's). The reader's *Remove password* action clears the column. Without a stored password the prompt appears on every open.
- **Reader UI** (`ReaderApp.svelte`): when the payload kind is `password-required`, the error state renders the **unlock form** — a password field (native type `password`), a **Remember this password** checkbox (unchecked by default), an *Unlock* action; when a stored password exists, the field pre-fills and the form offers *Remove password*. A wrong password keeps the form with an inline error (`field-error` treatment, the released form rules). A successful unlock with the checkbox checked writes the column; unchecked leaves nothing stored. The re-rendered page stack stays in the same window — no second window, no reload of the app.
- **Commands**: `app_pdf_page` / `app_pdf_outline` / `app_pdf_document` keep their signatures (the service reads the stored password from the row itself); one new command `library_set_password(id, password)` (set / clear). Whitelist + typed client updated.
- **Metadata** stays as today for encrypted files (the parser returns nothing; title falls back to the filename rule) — recorded as a limitation in the guide and the release notes.
- **Import-time covers**: a protected document generates a glyph cover at import (no password known yet); after the first successful unlock the document is enqueued again and the real cover replaces the glyph (the FR-16 appearance design of DR-231 applies unchanged).

### 3.4 Rename (FR-21)

- **Service** (`service.rs`): `rename_document(conn, id, new_name)`:
  1. Validate `new_name`: non-empty, no path separators, no reserved characters (`<>:"/\|?*`), no trailing dot or space; reject with a typed `InvalidName`.
  2. Collision: if the resulting path equals another document's `path` (the UNIQUE constraint) **or** a file already exists at that path in the same folder, reject with a typed `NameConflict` — no filesystem or DB change happened.
  3. `std::fs::rename(old, new)`; on failure a typed `Io` error, record untouched.
  4. In one transaction: `UPDATE documents SET path = ?, filename = ?` (and `title` re-derived from the new filename **only when `title_source = 'auto'`** — the title rule stated in FR-21). If the DB write fails, the file is renamed back (the compensating rename) and the error is returned — the record and the disk stay consistent.
  5. Enqueue the cover for the new identity (the key composes from the new path, M3); the stale entry is removed by the existing orphan sweep. The stored password travels with the row (it belongs to the document, not the name).
- **Commands**: `app_rename_document(id, new_name)` — thin wrapper; whitelist + typed client updated.
- **UI**: *Rename…* in the context menu and as a Details-dialog action (footer, beside the existing actions; applies only when the file exists). It opens a small dialog (the released Modal + inline form rules): one filename field prefilled with the current name, the folder shown read-only above it (the user renames the name, not the location), inline errors for `InvalidName` / `NameConflict`, Enter submits, Esc closes. On success: the row/card shows the new name through the normal store update; the Details dialog follows the new name (the open-document refresh path of DR-231 already re-reads the row).
- The relink and missing-detection logic needs no change: it resolves by `documents.path`, which is now the new path.

### 3.5 Open containing folder (UI-40)

- **Command**: `app_open_containing_folder(id)` — resolves the document row (the same typed resolution the reader-open command uses), returns `NotFound`/`Missing` typed errors when the row or file is gone, and calls `tauri_plugin_opener::reveal_item_in_dir([path])` (M6) — the Rust-side pattern of `app_open_data_dir`.
- **Capability**: `src-tauri/capabilities/default.json` gains `"opener:allow-reveal-item-in-dir"` (permission extension of an already-bundled plugin; no new dependency).
- **UI**: context-menu item + Details-dialog action, icon `folder` (already in the set); applies only when the file exists (missing documents show no item — the same `applies` mechanism the actions already use).

### 3.6 Bulk favorite toggle (UI-41)

- `actions.ts`: replace the two static bulk entries with one derived action computed from the current selection — `allSelectedFavorite ? bulkRemoveFavorite : bulkAddFavorite` — following the row/card favorite toggle's existing mechanism (M5); label and icon follow the action (filled star *Remove from favorites* when it would remove, outline star *Add to favorites* otherwise).
- `BulkBar.svelte`: renders the one control. The service side already supports batch favorite updates (the released bulk actions); no backend change.

### 3.14 Import progress granularity (D25, DR-279)
